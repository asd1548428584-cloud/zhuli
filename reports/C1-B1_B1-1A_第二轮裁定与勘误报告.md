## 2. B-1 最终裁定：结构与 FTS 分离

### 2.1 现状（三条路径的真实调用链）

`InboxDatabase.kt` 的三个入口，逐行核对（行号为当前 HEAD）：

| 入口 | 行 | 现状调用 | 每次执行时机 |
|---|---|---|---|
| `onCreate` | 317–318 | `createCoreTables(db)` + `createV16Tables(db)` | 仅新装（`version=0`） |
| `onOpen` | 339–340 | `createCoreTables(db)` + `createV16Tables(db)` | **每次打开数据库**（`if (!db.isReadOnly)` 内） |
| `onUpgrade`（`oldVersion<15` 分支） | 787、792 | `createCoreTables(db)` + `createV16Tables(db)` | 仅 `oldVersion<15` 的老库 |

`createCoreTables`（501–595）实际内容：`zhuli_entity`、`zhuli_agent_task`(+2 索引)、`zhuli_agent_step`(+1 索引)、**`zhuli_fact`（518）+ `idx_fact_slot/idx_fact_source/idx_fact_status`**、`zhuli_fact_vec`。
`createV16Tables`（602–635）：`zhuli_vec_queue`、`zhuli_tool_exec`(+2 索引)、`addColumnIfMissing(zhuli_agent_task, local)`。

**这就是 X-1 的物理位置**：`onOpen` 每次打开都会把 `zhuli_fact` 建回来。即使迁移第 12 步把它改名成 `zhuli_fact_v1`，下一次开库就会重新出现一张空的 `zhuli_fact`，而 v16 的写入方（若未删干净）会往这张假表里写，**数据静默丢失**。

另外两处 `onOpen` 行为必须一并考虑（否则"补建"会互相打脸）：

- `ensureColumns(db)`（846）：列漂移自愈，会 `ALTER TABLE ADD COLUMN`；
- `purgeOrphanEmbeddings(db)`：清孤儿向量，用 `orphanChecked` 保证每进程一次；
- `ensureFtsSync(db)`：FTS 同步，用 `ftsChecked` 保证每进程一次。

### 2.2 缺陷复述（三条，均为【实测】）

| 编号 | 缺陷 | 证据 |
|---|---|---|
| **B-1.1** | `onOpen` 写 `MemorySchema.ensureAll(db)`（单参），而规格里 `ensureAll` 要 `(db, prefs, cache, requested)` 四参 | v4.2.1 §4.8.2 行 1041；`ensureAll` 签名见同文档 `internal fun ensureAll(db, prefs, cache, requested)` |
| **B-1.2** | `ensureAll` 体内**只处理 FTS**：建 FTS 表 → 触发器 inspect/repair → 行数快检 → 重建 → 复核。**没有一行**创建 6 张基表或 15 个索引 | 同文档 `ensureAll` 实现，五步全部是 `FTS`/`FtsTriggers`/`safeQuickCount` |
| **B-1.3** | `ensureAll` 第一行 `if (requested == FtsMode.NONE) return FtsEnsureResult.None("requested_none")`。本机真实库无 `inbox_fts`、0 触发器（该 ROM 建不出 FTS，运行时档位必然不含 `TRIGGER`）→ **即使补上参数，在无 FTS 的 ROM 上 6 张表也不会被创建** | 同上；真实库 0 触发器为【实测】 |

### 2.3 裁定：拆成四个入口，权责互斥

| 入口 | 签名 | 谁调用 | 失败语义 |
|---|---|---|---|
| `createAll(db, withUnique: Boolean)` | 已存在，保留 | `onCreate`（`withUnique=true`）、`onUpgrade` 的 v17 段（`withUnique=false`） | **抛**。新装/升级失败应当 fail-loud 并回滚 |
| `ensureStructure(db): StructureReport` | **新增** | `onOpen` | **不抛**。逐对象 `try/catch`，失败记入报告，开库继续 |
| `ensureUniqueIndexes(db): UniqueIndexReport` | **新增** | `onOpen`；迁移第 10 步另走"预检→建→验"的抛异常路径 | **不抛**（`onOpen` 语义）。缺索引必须被报告，不得静默 |
| `ensureFts(db, prefs, cache, requested): FtsEnsureResult` | 即原 `ensureAll`，**改名** | `onOpen`（仅 `requested != NONE`） | **不抛**。降级返回，不改结构 |

**为什么 `ensureFts` 要改名而不是保留 `ensureAll`**：`ensureAll` 这个名字承诺了"全部结构"，而它只做 FTS。名字不改，下一个读代码的人还会以为 `onOpen` 已经建了表——B-1.3 正是这么发生的。

### 2.4 `ensureStructure` 的具体职责（B1-1B 实现）

```kotlin
internal data class StructureReport(
    val createdTables: List<String>,
    val createdIndexes: List<String>,
    val missingTables: List<String>,      // 建表失败
    val missingIndexes: List<String>,     // 建索引失败
    val driftedTables: List<String>,      // 表存在但列集不符，只报告不改
    val errors: List<String>,             // "对象: 原因"
) {
    val healthy: Boolean
        get() = missingTables.isEmpty() && missingIndexes.isEmpty() &&
                driftedTables.isEmpty() && errors.isEmpty()
}
```

执行顺序与规则：

1. **6 张基表**：逐张 `CREATE TABLE IF NOT EXISTS`（DDL 来自 `MemorySchema.DDL_*`，与 `createAll` 同一份常量，不复制）。
2. **12 个普通索引**：逐条 `CREATE INDEX IF NOT EXISTS`。
3. **结构指纹校验**：对每张表比 `pragma_table_info` 的列名序列与 `EXPECTED_COLUMNS[table]`；
   - 列数少 → `driftedTables`，**不** `ALTER`（v17 的加列必须走显式迁移，不能靠开库自愈，否则 v18 的加列会在老库上乱序发生）；
   - 列数多 → 同样记为 drift，只报告。
4. **不碰** `zhuli_fact` / `zhuli_fact_v1` / `zhuli_memory_fts`。
5. **任何单对象失败都不影响其它对象**：`try/catch` 包在**每个** DDL 外面，而不是整段外面。

**顺序约束**：`ensureStructure` 必须在 `ensureFts` **之前**调用。FTS 触发器引用 `zhuli_memory_item`，表不存在时建触发器会失败；反过来，结构失败不能阻止 FTS（FTS 有独立的 `None/AppSync/TriggerReady` 降级）。

### 2.5 `ensureUniqueIndexes` 的补建策略（与普通索引**不同**）

普通索引：`CREATE INDEX IF NOT EXISTS` 直接建，永远不会失败（除磁盘满）。

唯一索引：可能因为**存量重复**而失败，因此必须三步：

```
① 先看存在性：pragma_index_list(table) 里有该名字 → 跳过（不跑预检，零成本）
② 不存在才预检：
   P1 idx_ms_dedupe  : GROUP BY (source_type, ref_table, ref_id, ref_sub_id, content_hash) HAVING c>1
   P2 idx_mev_primary: GROUP BY memory_id WHERE role='PRIMARY' HAVING c>1
   P3 idx_mi_dedupe  : GROUP BY dedupe_key WHERE status IN ('ACTIVE','CANDIDATE') HAVING c>1
③ 预检 0 行 → CREATE UNIQUE INDEX；失败则 catch，记入 failed[index] = sqlite 错误码
   预检 >0 行 → **不建**，记入 blockedByDuplicates[index] = 组数
```

三条硬规则（对应任务书 §3 第 7–10 条）：

- **绝不自动删重复行**。删哪条是产品决策，不是实现细节。
- **绝不静默正常**。`blockedByDuplicates` / `failed` 非空 → `healthy=false`，且 `MemoryStore.selfCheck()` 必须逐条列出**缺失的索引名**（不是笼统的"结构异常"）。
- **绝不让开库崩溃**。唯一冲突是数据问题，不是启动阻塞问题；`onOpen` 抛异常会导致 `SQLiteOpenHelper.getWritableDatabase()` 每次调用都抛，App 起不来且无法自愈（用户只能清数据）。

**`onOpen` 补建唯一索引的代价**：只在索引缺失时才跑预检。索引存在时是 `pragma_index_list` 一次查询（微秒级），不影响启动。

| 情形 | 行为 | 用户可见后果 |

| 3 | Agent 工具 `save_memory`（"记住…"） | `ZhuliAgentTools.kt:151-169` | **`USER`** | `id` | `db.insert(InboxRecord(...))` 的返回值（`:151`）——先写 inbox，再拿行号 | **是**（且行内容 `source=chat`、`appLabel="备忘"`） |
| 4 | Agent 工具 `save_fact`（结构化事实） | `ZhuliAgentTools.kt:186-189` | `USER` | `0L` | 字面量 0 | 否 |
| 5 | 用户纠错 `correct_fact` | `MemoryRepo.kt:100-115` | `USER`（`:110`） | `0L`（`sourceId = 0L`） | 字面量 0；`sourceText = "用户纠正：…"` | 否 |
| — | 底层写入 | `MemoryRepo.kt:394-412`（`insert`） | 透传 `Fact.sourceType` | 透传 `Fact.sourceId` | 不产生语义 | — |
| — | 强化已有事实 | `MemoryRepo.kt:416-425`（`reinforce`） | 透传入参 | 透传入参 | **会覆盖**原行的 `source_type/source_id` | — |
| T | 单测 | `MemorySqliteTest.kt:86-87` | `USER` / `INFERRED` | `1L` / `2L` | 测试自己造的行号 | 语义上当作 inbox 行 |

**推论 1**：`source_id` 在**当前全部生产代码**里只有两种取值——`0`，或一个 `inbox.id`。没有第三种 id 空间（`zhuli_agent_step.id` 从未被传进来）。

**推论 2**：`source_type=USER` **不能**推出"没有行级来源"。路径 3 就是反例：用户说"记住 X"，系统先落一条 inbox 备忘，再以 `USER + 该行号` 写入事实。上一版报告推荐的 `USER → ref_table=''` 会把这条真实存在的引用**丢掉**。

**推论 3**：`reinforce()` 会把后到来源的 `source_id` 覆盖到旧行上（`MemoryRepo.kt:420-421`）。这是现有实现的证据链缺陷（C0.2 §1 已点名），迁移只能保留"最后一次强化"的引用——**必须如实说明，不能假装保真**。

### 3.2 来源语义表（三个概念的边界）

| 字段 | 回答什么问题 | 取值来自 | 迁移时的取值 |
|---|---|---|---|
| `source_type` | 这条证据**是什么性质**的来源（可信度分类） | 旧列 `source_type`（4 值）+ 载体细节（见 §5） | 映射到 C0.2 的 12 值词表 |
| `ref_table` | 原始证据**存在哪张表** | **载体**，不是 `source_type` | `source_id>0 → 'inbox'`，否则 `''` |
| `ref_id` | 那张表里的**哪一行** | 同上 | `source_id>0 → source_id 的十进制字符串`，否则 `''` |
| `ref_sub_id` | 同一行内的**子位置**（会话内消息 id、步骤 seq） | C1 无来源 | 恒 `''` |

C0.2 §2.3 对 `ref_table` 的注释是 `inbox / zhuli_agent_step / ConversationEntity / MemoryEntity`（【原文】）。`zhuli_fact` **不在**这个词表里。

### 3.3 `source_id > 0` 是否足以证明它是 inbox ID

**结论：在当前代码基线上，是；但迁移不得把它当公理，必须逐行验证。**

证据链（全部【实测】）：

1. `Ingest` 的 `sourceId: Long` 参数只有 4 个生产调用点（§3.1 表 1–4），实参分别是 `rec.id`（两次）、`db.insert(...)` 返回值（一次）、`0L`（一次）。
2. `pendingRows()` 与 `rowsInRangeAfter()` 的返回类型都是 `List<InboxRecord>`，`id` 字段由 `inbox` 表主键填充。
3. `db.insert(InboxRecord(...))` 返回 `inbox` 表的 rowid（`InboxDatabase.insert` → `SQLiteDatabase.insert`）。
4. `zhuli_fact.source_id` 的索引是 `idx_fact_source(source_type, source_id)`——设计上就是"按来源类型 + 来源行号"查，没有第二张表参与。
5. 全仓库没有 `INSERT INTO zhuli_fact` 的裸 SQL（除测试 `MemorySqliteTest.kt:373`，只插 subject/predicate/value，`source_id` 取默认 0）。

**为什么仍要逐行验证**：历史版本（v15 之前）的写入方可能传过别的 id；且 `deleteInboxByIds`（`InboxDatabase.kt:1265`）会删 inbox 行，**历史数据里必然可能出现悬空引用**。所以迁移规则是"**声明 + 校验**"，不是"假设"：

```sql
-- 迁移前统计（只读，不阻断）
SELECT COUNT(*) FROM zhuli_fact WHERE source_id > 0;                       -- 有引用
SELECT COUNT(*) FROM zhuli_fact f
WHERE f.source_id > 0
  AND NOT EXISTS (SELECT 1 FROM inbox i WHERE i.id = f.source_id);         -- 悬空
```

两个数字都写进迁移报告（`ref_total` / `ref_dangling`），后者对应 `dangling_ref` 计数。

### 3.4 裁定（方案 A′）

```kotlin
// 只由载体决定，不看 source_type
val hasRef   = sourceId > 0L
val refTable = if (hasRef) "inbox" else ""
val refId    = if (hasRef) sourceId.toString() else ""
val refSubId = ""
```

与上一版"方案 A"的差异只有一处，但很关键：

| 场景 | 上一版 A | **本轮 A′** | 差异后果 |
|---|---|---|---|
| `INBOX + inbox id` | `inbox` / id | `inbox` / id | 一致 |
| `USER + 0` | `''` / `''` | `''` / `''` | 一致 |
| **`USER + inbox id`** | `''` / `''`（**丢引用**） | **`inbox` / id** | A 会把"用户说过的那条备忘"这一可核查证据丢掉；A′ 保留 |
| `SYSTEM/INFERRED + inbox id` | `''` / `''` | `inbox` / id | 当前 0 样本；规则按载体，未来出现即正确 |
| `source_id>0` 但行已删 | `inbox` / id（未讨论） | `inbox` / id + `dangling_ref` 计数 | 明确表态：**保留引用，不静默丢弃** |

**为什么悬空也保留**：`ref_id` 是"当时指向哪一行"的历史事实。行被删了，事实仍然成立；读侧 `LEFT JOIN inbox` 得到 NULL 就知道"原文已不可读"，这比把 `ref_table` 清空、永远失去线索要好。清空后连"曾经有过原文"都无法判断。

### 3.5 六种边界的处理

| 边界 | 处理 | `independent_key` |
|---|---|---|
| `source_id = 0` | `ref_table=''`、`ref_id=''`；证据靠 `excerpt`（≤120、已脱敏）+ `content_hash` 保留 | `"$type|-|$hash"` |
| `source_id > 0`，inbox 行在 | `ref_table='inbox'`、`ref_id=id` | `"$type|inbox|$id"` |
| `source_id > 0`，行不存在 | 同上，另计 `dangling_ref` | 同上（仍是同一证据文件） |
| `USER + inbox id` | 同"行在"分支 | `"USER_MESSAGE|inbox|$id"` |
| `SYSTEM/INFERRED + inbox id` | 同"行在"分支（无样本，规则先行） | 同上形式 |
| 无行级来源的 USER | `ref_table=''`；`excerpt` 就是唯一证据；`trust=3` | `"$type|-|$hash"` |

**"无行级来源的 USER 如何保留证据"**：`source_text` 是唯一原文，迁移时截 120 字并过 `SensitiveGuard.redact` 存进 `excerpt`，同时存 `content_hash`。这满足 C0.2 §5.3 的幂等要求（同文本重放不新增 source 行），也满足"凭什么"的 UI 需求。**注意**：`excerpt` 是脱敏后的片段，原文不保留——这一点必须在 C1 报告里写明，不能让用户以为"记忆里存了原话"。

### 3.6 唯一键与 `independent_key`：六个样本的预期结果

`idx_ms_dedupe` 定义（【原文】C0.2 §2.3 行 260）：
`UNIQUE (source_type, ref_table, ref_id, ref_sub_id, content_hash)`

| # | 样本 | 5 元组 | source 行数 | evidence | `independent_key` | 独立来源数 |
|---|---|---|---|---|---|---|
| 1 | `USER + 0`，文本 A | `(USER_MESSAGE, '', '', '', hA)` | 1 | 1 PRIMARY | `USER_MESSAGE\|-\|hA` | 1 |
| 2 | `USER + inbox 5`，文本 B | `(USER_MESSAGE, 'inbox', '5', '', hB)` | 1（与 #1 不同行） | 1 | `USER_MESSAGE\|inbox\|5` | 1 |
| 3 | `INBOX + inbox 7`（sms），文本 C | `(INBOX_SMS, 'inbox', '7', '', hC)` | 1 | 1 | `INBOX_SMS\|inbox\|7` | 1 |
| 4 | `source_id=9` 但行已删，文本 D | `(INBOX_NOTIFICATION, 'inbox', '9', '', hD)` | 1（照建） | 1 | `INBOX_NOTIFICATION\|inbox\|9` | 1，另计 `dangling_ref=1` |
| 5 | 两条事实**同来源同文本**（同一条通知抽出两条记忆） | 5 元组相同 → **同一 source 行** | 1 | **2**（不同 `memory_id`，`PK(memory_id,source_id)` 不冲突） | 相同 | **1**（正确：同一证据） |
| 6 | 两条事实**同来源不同文本**（同一条通知里的两句话） | `hC`、`hC2` → 2 行 | 2 | 2 | **相同** | **1**（正确：同一证据文件） |

**关键不变式**：`COUNT(DISTINCT independent_key)` 必须等于"独立证据文件数"，不能因为 `ref_table` 写错而把一个来源拆成两个，也不能把两个来源合并成一个。

**上一版 `ref_table='zhuli_fact'` 的后果（量化）**：
- #6 的两行会得到 `INBOX|zhuli_fact|7`，仍然相同 → 独立性计数**碰巧正确**；
- 但 #2 的 `USER|''|''` 与 #1 的 `USER|''|''` 会**撞成同一个 key**（都走无 ref 分支 → 实际用 hash，不撞）；真正的问题是 `ref_table` 指向一张**迁移后不存在**的表，任何"按 ref_table 回查原文"的实现都会拿到 `no such table` 或查错表。

### 3.7 12 列能否无损表达（结论：能，不扩列）

| 需要的语义 | 现有列 | 是否够 |
|---|---|---|
| 来源性质（12 值） | `source_type` | 够（词表见 §5） |
| 证据在哪张表哪一行 | `ref_table` + `ref_id` | 够 |
| 行内子位置 | `ref_sub_id` | 够（C1 恒空） |
| 独立性 | `independent_key` | 够 |
| 原文片段（脱敏） | `excerpt` | 够（≤120） |
| 幂等 | `content_hash` | 够 |
| 可信度分级 | `trust` | 够 |
| 时间 | `captured_at` / `created_at` | 够 |
| 摘录清除但保留引用 | `purged_at` | 够 |

**不需要新增列。** 唯一"表达不了"的是 `reinforce()` 造成的**多来源覆盖**（§3.1 推论 3）：旧行只保留最后一次的 `source_id`，之前的来源在旧表里就已经丢了。这不是 schema 能修的，是 B4 重写 `MemoryRepo` 时要停止的行为——迁移只能如实记录"这是最后强化来源"，并在报告里注明。

## 4. B-3 最终裁定：失效时间边界

### 4.1 原文规则（按状态分支，不是统一表达式）

v4.2.1 行 1322（【原文】，`§5.x` 列映射表的注释行）：

```
invalidated_at | SUPERSEDED → (valid_to ?: updated_at)；DELETED → updated_at；其它 0
```

配套约束：

- **不变量 #4**（v4.2.1 行 1638）：`COUNT(*) WHERE status='SUPERSEDED' AND invalidated_at=0` 必须为 0；
- **T-M37**（v4.2.1 行 3904）：SUPERSEDED 行 `valid_until=0`、`invalidated_at=原 valid_to`；**DELETED 行 `valid_until=0`、`invalidated_at=原 updated_at`**；
- 旧 `valid_to` 的**唯一**去处就是 `invalidated_at`（行 779 第 12 项）。

### 4.2 上一版报告写错在哪

上一版（§8 B-3）把规则写成统一表达式：

```kotlin
invalidatedAt = if (validTo > 0) validTo else updatedAt
```

两处错：

1. **漏了 DELETED 分支**。`DELETED` 行即使 `valid_to > 0`，也必须用 `updated_at`（T-M37 明文），统一表达式会取 `valid_to`，与用例冲突。
2. `updatedAt = 0` 时结果是 0，SUPERSEDED 行直接违反不变量 #4。

第一处是我上一版的实质性错误，本轮修正；第二处是审阅方指出的，成立。

### 4.3 最终规则

```kotlin
fun invalidatedAtFor(status: FactStatus, validTo: Long, updatedAt: Long, migrationNow: Long): Long =
    when (status) {
        FactStatus.SUPERSEDED -> when {
            validTo   > 0 -> validTo
            updatedAt > 0 -> updatedAt
            else          -> migrationNow      // 兜底：不变量 #4 要求非 0
        }
        FactStatus.DELETED    -> when {
            updatedAt > 0 -> updatedAt          // T-M37：DELETED 用 updated_at
            else          -> migrationNow      // 兜底，见 §4.4 的缺口
        }
        else -> 0L                              // ACTIVE / CANDIDATE
    }
```

三条附带要求：

- `migrationNow` 必须是**同一个值**（迁移开始时取一次），不能每行 `System.currentTimeMillis()`——否则同一批数据出现几十毫秒漂移，回归比对无法断言。
- 兜底触发时计数 `ts_fallback++`，写进迁移报告（不含内容）。
- **不得**改动其它时间字段：`valid_from` 原值保留、`valid_until` 恒 0、`observed_at` 按 `原值→created_at→now`、`recorded_at=created_at`、`updated_at=原值→created_at`（【原文】行 770–790）。

### 4.4 不变量覆盖缺口（新发现）

不变量 #4 只约束 `SUPERSEDED`。但 `DELETED` 行若 `invalidated_at=0`，`asOfBelief` 的谓词 `(invalidated_at=0 OR :at < invalidated_at)`（v4.2.1 行 3251）会让一条**已删除**的记忆在信念线里**永久可见**。这不是理论风险：迁移里 `DELETED` 走 `updated_at`，若该列也是 0（旧库早期行可能没写过 `updated_at`），就会落 0。

**建议新增不变量 #7**（本轮提出，需批准）：

```sql
SELECT COUNT(*) FROM zhuli_memory_item
WHERE status IN ('SUPERSEDED','DELETED') AND invalidated_at = 0;   -- 期望 0
```

批准前，`migrationNow` 兜底已经能保证本库两类行都不落 0；新增不变量只是把"实现自觉"变成"验收可查"。

### 4.5 测试设计（三正例 + 两异常）

| 编号 | 构造 | 期望 |
|---|---|---|
| B3-1 | `status=SUPERSEDED, valid_to=1700000000000, updated_at=…` | `invalidated_at = 1700000000000` |
| B3-2 | `status=SUPERSEDED, valid_to=0, updated_at=1690000000000` | `invalidated_at = 1690000000000` |
| B3-3 | `status=SUPERSEDED, valid_to=0, updated_at=0` | `invalidated_at = migrationNow`；`ts_fallback=1`；不变量 #4 通过 |
| B3-4 | `status=DELETED, valid_to=1700000000000, updated_at=1690000000000` | `invalidated_at = 1690000000000`（**不是** valid_to） |
| B3-5 | `status=DELETED, valid_to=0, updated_at=0` | `invalidated_at = migrationNow`；`ts_fallback=1` |
| B3-6 | `status=ACTIVE / CANDIDATE` | `invalidated_at = 0`（不论 valid_to 是否 >0） |

B3-4 是**回归上一版错误**的用例：如果实现者照上一版写统一的 `validTo ?: updatedAt`，B3-4 必须红。

### 4.6 与审阅方建议的差异（用证据说明）

审阅方建议：

```kotlin
invalidatedAt = when {
    validTo > 0 -> validTo
    updatedAt > 0 -> updatedAt
    else -> migrationNow
}
```

方向完全正确（补兜底），但**缺状态分支**：对 `DELETED + valid_to>0` 的行会得到 `valid_to`，而 T-M37 要求 `updated_at`。真实库里 DELETED 行是否带 `valid_to` 取决于它是否曾被替代过（`supersede` 会写 `valid_to`，之后 `deleteFact` 又会改成 DELETED）——**这种行是存在的**：

```sql
-- 只读核查（本库 0 行：只有 1 条 SUPERSEDED、无 DELETED，见附录 B）
SELECT COUNT(*) FROM zhuli_fact WHERE status='DELETED' AND valid_to>0;
```

所以最终规则保留状态分支（§4.3），兜底沿用审阅方的 `migrationNow`。两者不冲突，是"在正确形状上加兜底"。

## 5. B-4（本轮新增）：来源类型 12 值词表的映射缺口

### 5.1 缺口证据

| 证据 | 内容 |
|---|---|
| C0.2 §2.3 行 243–245（【原文】） | `source_type` 的取值注释为 12 值：`USER_MESSAGE / USER_CONFIRMATION / INBOX_NOTIFICATION / INBOX_SMS / INBOX_SHARE / CHAT_MESSAGE / AGENT_TASK / TOOL_RESULT / EXTERNAL_API / MODEL_INFERENCE / IMPORT / MIGRATION` |
| v4.2.1 全文（【实测】） | `grep -c "USER_MESSAGE\|INBOX_NOTIFICATION\|CHAT_MESSAGE\|MODEL_INFERENCE"` = **0**。该文档从未提及这 12 个值，也没有任何"旧 4 值 → 新 12 值"的映射表 |
| v4.2.1 §5.5 行 1434（【原文】） | `SourceKey(sourceType, …)` 里的 `sourceType` 直接来自旧列 `c.str("source_type")`（即 `INBOX/USER/INFERRED/SYSTEM` 之一） |
| 现有 Kotlin（【实测】） | `enum class SourceType { INBOX, USER, INFERRED, SYSTEM }`（`MemoryTypes.kt:74-86`） |

**结论**：照 v4.2.1 现状实现，迁移会把 `'INBOX'` / `'USER'` 写进一个按设计只应存 `'INBOX_NOTIFICATION'` / `'USER_MESSAGE'` 的列。这不是"风格问题"——C2 的 `REPEATED_OBSERVATION` 判定要按 `source_type='MODEL_INFERENCE'` 限制"模型不能自己给自己作证"（C0.2 §5.4 行 841），旧值 `INFERRED` 不会命中，**推断出来的记忆会被当成独立证据**。

### 5.2 两种映射方案

**方案 粗（4→4）**：`INBOX→INBOX_NOTIFICATION`、`USER→USER_MESSAGE`、`INFERRED→MODEL_INFERENCE`、`SYSTEM→AGENT_TASK`。
- 优点：零 JOIN、规则最短；
- 缺点：短信与通知都变成 `INBOX_NOTIFICATION`，`INBOX_SMS`、`INBOX_SHARE`、`CHAT_MESSAGE`、`USER_CONFIRMATION` 四个值永远用不上；来源可信度分级失去一半分辨率。

**方案 细（载体优先，推荐）**：先用 §3.4 的 `ref_table='inbox'` 判断，再查 `inbox.source`（取值 `notification / sms / share / link / chat`，`InboxRecord.kt:34-38`）：

| 旧 `source_type` | 载体条件 | 映射为 | 依据 |
|---|---|---|---|
| `INBOX` | `inbox.source = 'sms'` | `INBOX_SMS` | 载体的真实类型 |
| `INBOX` | `inbox.source = 'notification'` | `INBOX_NOTIFICATION` | 同上 |
| `INBOX` | `inbox.source = 'share' / 'link'` | `INBOX_SHARE` | 同上 |
| `INBOX` | `inbox.source = 'chat'` | `CHAT_MESSAGE` | 同上（`save_memory` 落的备忘行就是 chat） |
| `INBOX` | 悬空（行已删）或未知值 | `INBOX_NOTIFICATION` | 无载体可查，取最保守的通用值 |
| `USER` | `source_text` 以 `"用户纠正："` 开头 | `USER_CONFIRMATION` | `MemoryRepo.correct()` 固定写这个前缀（`:112`），且 `confidence=1.0` |
| `USER` | 其它 | `USER_MESSAGE` | — |

**推荐细则**，因为：
1. 迁移时本来就要跑 `EXISTS(inbox)` 校验（§3.3），`LEFT JOIN inbox` 是**顺带**拿到 `source`，没有额外扫描成本；
2. `INBOX_SMS` 与 `INBOX_NOTIFICATION` 的可信度不同（短信是用户账户绑定的强证据，通知可能是任意 App 推送），C2 的排序要用；
3. `MIGRATION` 值**不使用**——它是给"外部导入"预留的，把所有迁移行标成 `MIGRATION` 会丢掉全部来源信息。

### 6.3 D-3｜sensitivity：C0.2 只看 content 是错的

**原文**：C0.2 §8.1 第 28 条（行 1267）：`SensitiveGuard.reason(content)` → SECRET 隔离 / SENSITIVE 1 / NORMAL 0；**只看 content**，来源摘录单独脱敏。

### 6.4 D-4｜索引数量：C0.2 §8.9 是旧口径

**原文**：C0.2 §8.9

```

10 CREATE UNIQUE INDEX idx_mi_dedupe      ← 必须最后
```

**v4.2.1**：12 个普通索引 + 3 个唯一索引；第 10 步是"预检 3 → 按 `idx_ms_dedupe` → `idx_mev_primary` → `idx_mi_dedupe` 顺序建 → 逐条验证"（§5.2 / §5.2.1，v4 修 P0-1 的直接产物）。

**判定**：C0.2 的"5 个普通索引 + 只建 1 个唯一"是 v3 之前的口径，照它实现会让升级库缺 2 个唯一约束（同一证据重复插入、一条记忆两个 PRIMARY 来源，都不报错）。必须改。

**动作**：E-04。

### 6.5 D-5｜`sqlite_sequence`：C0.2 只有一句 UPDATE

**原文**：C0.2 §8.6 第 3 条：`UPDATE sqlite_sequence SET seq=(SELECT MAX(id) FROM zhuli_memory_item) WHERE name='zhuli_memory_item'`。

**问题**（v4.2.1 §5.7 已论证）：`sqlite_sequence` 的 `name` 上没有唯一约束也没有索引（本机 `PRAGMA index_list('sqlite_sequence')` 返回 0 行）；没有唯一冲突，`INSERT OR REPLACE` 会退化成普通 `INSERT`，每次对齐多一行。若库里已有重复行，`UPDATE ... WHERE name=?` 会一次改多行。

**修订后的四步**：① 收敛重复行（只留 `rowid` 最大） → ② `UPDATE` → ③ 读 `changes()`，为 0 才 `INSERT` → ④ 断言 `COUNT(*)==1` 且 `seq >= MAX(id)`。

**实测**（【实测】）：真实库 `sqlite_sequence` 4 行、0 重复、9 张自增表——说明当前库是干净的，但代码必须能处理"被旧版本写脏"的库。

**动作**：E-05。

### 6.6 D-6｜`user_version`：不由迁移代码写

**原文**：C0.2 §8.9 第 13 步 `PRAGMA user_version = 17`。**v4.2.1 X-6**：不写，交给 `SQLiteOpenHelper`——`onUpgrade` 返回后 helper 自己 `setVersion(mNewVersion)`；在事务内改版本号会出现"版本号到了 17 但迁移没提交"的窗口。

**判定**：v4.2.1 正确。附带一条实现纪律：**预演脚本（纯 Python、无 helper）要写 `user_version=17`**，那是脚本自己的事，不能因为"文档说别写"就漏掉。

**动作**：E-06。

### 6.7 D-7｜表计数口径：24 是"设计条目数"，不是"运行期表数"

## 10. 结论

### 10.1 是否具备进入 B1-1B 的条件

**具备，但分两段放行。**

| 阶段 | 可否开工 | 前置条件 |
|---|---|---|
| **B1-1B**（`MemorySchema` 结构层：6 表 + 12 普通索引 + `ensureStructure` + `ensureUniqueIndexes` + DDL 常量） | **可以** | 采纳 E-01 / E-04 / E-07 / E-09 中与本阶段相关的部分；`ensureFts` 只留常量与 TODO |
| **B1-3**（`MemoryMigrator` 迁移编码） | **暂不可以** | 必须先批准 B-2（E-10/E-11）与 B-4（E-13）；否则 `ref_table` 与 `source_type` 写错，事后要重算 `idx_ms_dedupe` 与全表 `independent_key` |
| **B1-2**（FTS 运行时） | 暂不排 | 结构层稳定后再开；三档降级不得提前塞进 B1-1B |
| **B1-4**（测试与验收） | 暂不排 | 先出 115 条的逐条映射表，锁定阈值 |

### 10.2 与上一版报告的差异（自我修正）

| 项 | 上一版 | 本轮 | 原因 |
|---|---|---|---|
| B-3 规则 | `validTo ?: updatedAt`（统一） | 按状态分支 + `migrationNow` 兜底 | 漏了 DELETED 分支，与 T-M37 冲突 |
| B-2 推荐 | 方案 A：`USER → ref_table=''` | 方案 A′：`USER + inbox id → 'inbox'` | 会丢掉 `save_memory` 的真实引用 |
| D-8 算术 | "57−3=54；若 7 已实现，剩余 47" | 47 + 18 + 50 = 115；阈值 367 偏低 70 | 未把 v4.2.1 新增的 68 条算进去 |
| D-1 | 7 处列数错 | 7 处列数错 + 3 处表名错 | 这轮才查 `chat_log`/`skills`/`embeddings` 的真实常量名 |

### 10.3 一句话

DDL 与索引本身没有问题；出问题的是**三处把"结构"和"能力"混在一起的地方**（`ensureAll` 兼管 FTS、`ref_table` 兼管来源类型、`invalidated_at` 兼管两种状态），以及**两处把"设计条目"当成"运行期事实"的数字**（24 张表、57 条用例）。这一轮把这五处全部拆开了。
