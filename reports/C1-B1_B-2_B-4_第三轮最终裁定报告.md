### 2.6 关键发现：同一条 inbox 行会被两条路径各写一次

这是本轮最重要的新发现，也是 B-4.1 的裁决依据。

【代码实测】：

1. `save_memory` 先 `db.insert(InboxRecord(source=chat, appLabel="备忘", pendingExtract=0, category=f.category))`（`ZhuliAgentTools.kt:151-165`），再 `ingest(USER, id)`。
2. `MemoryBackfill` 用 `rowsInRangeAfter(fromTs, toTs, cursor, 50)`（`InboxDatabase.kt:1103-1108`）取行——**SQL 里没有 `source` 过滤**：

```sql
SELECT * FROM inbox WHERE received_at BETWEEN ? AND ? AND id > ?
ORDER BY id ASC LIMIT ?
```

3. 回填在 UI 上可达：`ZhuliMemoryPage.kt:213` 与 `:222` 分别以"近 30 天 / 近 90 天"启动回填。
4. 回填对每一行调 `repo.ingest(drafts, SourceType.INBOX, rec.id, …)`（`MemoryBackfill.kt:124-127`）。

**因此**：一条"记住 X"产生的备忘行（`source=chat`），既会由 `save_memory` 以 `USER` 写入，也会被之后的一次回填以 `INBOX` 重新抽取。

两条事实若值相同，`ingest` 的"同值"分支会命中并调用 `reinforce()`（`MemoryRepo.kt:416-425`），**把 `source_type/source_id` 覆盖成后到的 `INBOX`**——也就是说，旧库里一条 fact 的 `source_type` 记录的是**最后一次写入者的身份**，不是这条证据的性质。这是既有实现的缺陷（C0.2 §1 已点名"证据链在写入时就断了"），迁移无法还原。

如果两条事实的值**不完全相同**（例如回填抽取出的 predicate 有差异），就会留下两条 fact，指向**同一个 inbox 行**，但 `source_type` 分别是 `USER` 与 `INBOX`。这正是 §3.3 要解决的问题。

## 3. B-4.1 裁定：`USER + inbox.source=chat` 到底映射成什么

### 3.1 矛盾的准确表述

第二轮的表把 `USER` 的普通情况映射成 `USER_MESSAGE`，只在 `INBOX` 分支上看载体。于是：

| 事实 A（`save_memory` 写） | 事实 B（回填重抽同一行） |
|---|---|
| `source_type=USER`、`source_id=5`、`inbox.source=chat` | `source_type=INBOX`、`source_id=5`、`inbox.source=chat` |
| 第二轮：`USER_MESSAGE` | 第二轮：`CHAT_MESSAGE` |
| `independent_key = USER_MESSAGE\|inbox\|5` | `independent_key = CHAT_MESSAGE\|inbox\|5` |

同一个证据文件（inbox 第 5 行）被算成 **2 个独立来源**。这直接违反 C0.2 §5.2 对 `independent_key` 的定义——"回答两个来源算不算同一个"，其示例表（行 816）明确写"同一条通知里的两句话 → `INBOX_NOTIFICATION|inbox|123` → **1**（同一证据文件）"。

### 3.2 三个候选规则

| 方案 | 规则 | 同一行的 A/B 两条事实 | 结论 |
|---|---|---|---|
| **R1 类型优先**（第二轮） | `USER→USER_MESSAGE`，`INBOX→按载体` | 2 个独立来源 | **错**：把一份证据算成两份 |
| **R2 载体优先（无条件）** | 有有效载体就按 `inbox.source`，`INFERRED` 也不例外 | 1 个 | 会丢掉 `MODEL_INFERENCE`，破坏 C2 的"模型不能自证"规则 |
| **R3 模式优先 + 渠道其次**（本轮） | 先判断言模式（`INFERRED`/`SYSTEM`），再判载体，最后按旧类型兜底 | 1 个 | **采用** |

### 3.3 为什么 R2 不能无条件：`MODEL_INFERENCE` 是模式，不是载体

C0.2 §5.4（行 840-842）规定 `REPEATED_OBSERVATION` 必须满足：

```
COUNT(DISTINCT independent_key) >= 3
AND 其中 MODEL_INFERENCE 类型的来源 <= 1      -- 模型不能自己给自己作证
```

如果一条 `INFERRED` 事实因为带了 inbox 引用而被映射成 `INBOX_NOTIFICATION`，这条约束就失效了：模型从同一条通知里推出 5 条互相印证的"事实"，会被当成 5 个独立来源。**这比丢掉载体信息严重得多。**

`SYSTEM` 同理：它表达"这条是系统能力写的"（日历/提醒），不是"证据存在哪"。

### 3.4 裁定：7 步优先级（最终规则）

输入：`legacy`（旧 `source_type` 原文，`trim()` 后）、`sid`（旧 `source_id`）、`carrier`（若 `sid>0` 且 `inbox` 行存在，则为其 `source`，否则 `null`）、`text`（旧 `source_text`）。

| 步 | 条件 | 结果 | 理由 |
|---|---|---|---|
| **1** | `legacy == "INFERRED"` | `MODEL_INFERENCE` | 模式优先，保住 C2 的自证约束 |
| **2** | `legacy == "SYSTEM"` | `AGENT_TASK` | 同上；**零样本、未经证实**（§2.7） |
| **3** | `legacy == "USER"` 且 `text` 以 `"用户纠正："` 开头 | `USER_CONFIRMATION` | 与 C0.2 §8.3 的 basis 判定条件完全一致（`MemoryRepo.kt:110-112` 是唯一写入方） |
| **4** | `sid > 0` 且 `carrier != null` 且 `carrier` 已知 | 按载体：`notification→INBOX_NOTIFICATION`／`chat→CHAT_MESSAGE`／`share|link→INBOX_SHARE`／`sms→INBOX_SMS` | 载体决定"证据从哪来"；`USER` 与 `INBOX` 在这一步合并处理 |
| **5** | `legacy == "USER"` | `USER_MESSAGE` | 用户直接陈述、无可核查载体 |
| **6** | `legacy == "INBOX"` | `INBOX_NOTIFICATION` | 有 inbox 通道但无可用行；取通用值，计 `default_mapping` |
| **7** | 其它（未知 / `NULL` / 空串） | `INBOX_NOTIFICATION` + `payload_json.legacy_source_type` | 最低可信档，不冒充 USER/模型；原值留痕，计 `unknown_source_type` |

**步 4 的"已知"**：`notification` / `chat` / `share` / `link` / `sms` 五个值。其它值（含 `NULL`）视为"载体未知"，落到步 5–7，并计 `unknown_carrier`。

### 3.5 被否决的写法与原因

| 写法 | 为什么不行 |
|---|---|
| `USER` 永远 `USER_MESSAGE` | §3.1：同一证据被算成两个独立来源 |
| 无条件载体优先（含 `INFERRED`） | §3.3：破坏 `MODEL_INFERENCE <= 1` 约束 |
| `source_type` 直接用旧 4 值 | 不在 C0.2 §2.3 的 12 值词表内；且 §10.4 的投影会 `valueOf` 失败 |
| 全都映射成 `MIGRATION` | 丢掉全部来源信息，等于把 12 值塌成 1 值 |

### 3.6 代价与补偿：三个信号的分工

裁定后，"用户说的"不再由 `source_type` 表达。必须确认它没丢：

| 信号 | 承载字段 | 规则 | 证据 |
|---|---|---|---|
| 证据从哪来（渠道） | `source_type` | 本轮的 7 步 | §3.4 |
| 说话人有多可信 | `trust` | `USER → 3`，其它 `1`（**按旧类型判，不看新类型**） | v4.2.1 §5.5 行 1451 |
| 断言性质（陈述/纠正/规则/推断） | `confidence_basis` | 按旧类型 + 前缀（`USER`→`USER_STATED`，`USER`+前缀→`USER_CONFIRMED`，`INBOX`→`RULE_EXTRACTED`，`INFERRED`→`MODEL_INFERRED`，`SYSTEM`→`EXTERNAL_VERIFIED`） | C0.2 §8.3 行 1322-1328 |

**因此**：`USER + chat` → `source_type=CHAT_MESSAGE`、`trust=3`、`basis=USER_STATED`、`confidence≤0.95`。三类信息各归其位，没有一项丢失。

**但有一处必须一起改**：C0.2 §10.4（行 1757）的兼容层投影写的是

```
sourceType = source.source_type 反解（SourceType.valueOf，失败 INBOX）
```

旧枚举只有 `INBOX/USER/INFERRED/SYSTEM`，`SourceType.valueOf("CHAT_MESSAGE")` 必然失败 → 回落 `INBOX`。后果：**记忆页每条"用户说的"都会显示"来源 INBOX"**（`ZhuliMemoryPage.kt:141`、`:248`、`ZhuliAgentTools.kt:81` 都直接打印 `sourceType`），UI 回归可见。

修正：投影改从 `confidence_basis` 反解（`USER_*`→`USER`、`MODEL_INFERRED`→`INFERRED`、`EXTERNAL_VERIFIED`→`SYSTEM`、其余→`INBOX`）。见 errata **E-15**。这是本轮新增的**必改项**，属于 B1-1B 的兼容层。

## 4. B-4.2 裁定：12 值词表逐项

### 4.1 目标值总表

| 目标值 | 旧数据来源 | 迁移判定条件 | 真实样本 | 证据 | 不确定性处理 |
|---|---|---|---|---|---|

## 5. B-4.3 裁定：`ref_table` / `ref_id` 规则

### 5.1 三个概念

| 字段 | 回答 | 取值 |
|---|---|---|
| `source_type` | 证据**是什么性质**（渠道/模式） | §4.1 的 12 值 |
| `ref_table` | 证据**存在哪张物理表** | `'inbox'` 或 `''` |
| `ref_id` | 那张表里的**哪一行** | 十进制字符串，或 `''` |

**关键纪律**：`ref_table` 只由 `source_id` 是否有行级指向决定，**与 `source_type` 无关**。`CHAT_MESSAGE + ref_table='inbox'` 是合法组合（对话产生的条目落在 inbox），`USER_MESSAGE + ref_table='inbox'` 也合法（用户说的话被落成备忘行）。

### 5.2 判定表

| `source_id` | inbox 行 | `ref_table` | `ref_id` | 计数 | 备注 |
|---|---|---|---|---|---|
| `= 0` | — | `''` | `''` | — | 无行级引用；`independent_key` 走 hash 分支 |
| `> 0` | **存在** | `'inbox'` | `source_id.toString()` | `ref_total` | 正常 |
| `> 0` | **不存在** | `'inbox'` | `source_id.toString()` | `ref_total` + `dangling_ref` | **保留原值**，不静默丢弃 |
| `< 0` | — | `''` | `''` | `invalid_source_id` | 负值不可能是 rowid；原值进 `payload_json` |

**修正 C0.2 §8.4 的 `hasRef = (source_id != 0)`**：负值会被判成"有引用"。必须改成 `source_id > 0`。见 E-16。

### 5.3 悬空引用：保留 + 可判定，不扩列

**保留的理由**（三条）：

1. `ref_id` 是"当时指向哪一行"的历史事实，行被删不等于这个事实没发生过；
2. 清空后，"曾经有过原文"这条信息也一起消失，未来连追溯都不可能；
3. 同一条已删行的两条事实，靠 `ref_id` 才能共享 `independent_key`（仍算 1 个来源）；清空后会退化成 hash 分支，把一份证据算成多份。

**如何避免被当成有效证据**：读侧强制 `LEFT JOIN`，并规定返回值语义：

```sql
SELECT s.*, i.id AS inbox_id          -- inbox_id 为 NULL 即悬空
FROM zhuli_memory_source s
LEFT JOIN inbox i ON s.ref_table = 'inbox' AND i.id = s.ref_id
```

**类型说明**（【设计推导】，需 B1-3 实测确认）：`ref_id` 是 TEXT、`inbox.id` 是 INTEGER；SQLite 在比较时按列的 INTEGER 亲和性转换 TEXT 值，因此该 JOIN 能走 `inbox` 的主键索引。若实测走不通，退化为 `CAST(s.ref_id AS INTEGER) = i.id`，并在 B1-3 记录代价。

**读取契约**（C2 必须遵守）：

```kotlin
sealed interface RefResolution {
    data class Exists(val inboxId: Long) : RefResolution
    data object Missing : RefResolution          // 悬空：原文已不可读
}
fun resolveRef(source: MemorySource): RefResolution
```

UI 与工具在 `Missing` 时必须显示"原文已删除"，**不得**把 `ref_id` 当有效行号去查别的东西。

### 5.4 Schema 表达不了的两项（报告，不扩列）

| 语义 | 能否用 12 列表达 | 处理 |
|---|---|---|
| `ref_exists`（引用当前是否可解析） | **不能**（它是随 `inbox` 增删变化的派生量，存下来就会过期） | 不存，读侧 `LEFT JOIN` 派生；不扩列 |
| 负 `source_id` 的原始值 | **不能**（`ref_id=''` 会丢；写 `'-1'` 会让 `ref_table=''` 与"有 ref"矛盾） | 写 `payload_json.legacy_source_id`，计 `invalid_source_id` |

`payload_json` 是既有 40 列之一，§5.3 已用它存 `legacy_status`（v4.2.1 不变量 #6 就查这个键），本轮沿用同一模式，**不新增列**。

### 6.3 七个问题的逐项回答

| # | 问题 | 结论 | 依据 |
|---|---|---|---|
| 1 | 同一证据是否会被错误拆成多个独立来源 | **R1（第二轮）会；R3 不会** | S3/S4 在新规则下同键合并；R1 会得到 `USER_MESSAGE` 与 `CHAT_MESSAGE` 两键 |
| 2 | 不同来源是否会被错误合并 | **不会** | 不同 `ref_id`（S3 vs 其它行）、不同载体（S3 vs S5）、不同模式（S5 vs S9）都产生不同键 |
| 3 | `USER + chat` 是否与 `CHAT_MESSAGE` 冲突 | **不冲突，合并是期望行为** | S3/S4：同一 inbox 行的同一段文本，本就该是一条证据 |
| 4 | 同一 inbox 记录被多条旧记忆引用 | 文本相同 → **1 source 行 + N 条 evidence**；文本不同 → **N 条 source 行 + 1 个 `independent_key`** | 5 元组含 `content_hash`；`independent_key` 不含 hash |
| 5 | 悬空引用是否造成错误去重 | 同旧类型 + 同 id → 同键（正确）；**不同旧类型 + 同 id → 2 键（残余风险 R-2）** | S7/S8 |
| 6 | 迁移后的去重键能否稳定复现 | **能**：映射输入全是静态列，时间由 `now` 参数注入（§7.1） | — |
| 7 | 映射规则未来调整是否需要全表重算 | **需要**：`zhuli_memory_source.source_type` 首列 + `independent_key` 全段；`zhuli_memory_item` 的 `dedupe_key` 不受影响 | §7.2 |

**残余风险 R-2（S7/S8）**：同一条**已删** inbox 行，若被 `USER` 与 `INBOX` 两条路径各写过一次，迁移后是两个 `independent_key`，独立来源数为 2。这是"载体已不可读"的必然代价——除非引入跨行推断（把同一 `ref_id` 的所有事实统一成一种类型），而那会让迁移结果依赖"该 id 出现过几次"，反而更难审计。**建议接受**，在迁移报告里计 `dangling_ref` 让风险可见。

### 6.4 键定义是否需要改

**不需要改定义**。`idx_ms_dedupe` 的 5 元组与 `independent_key` 的构成在语义上是对的：`source_type` 属于"证据身份"的一部分（同一行文本被模型推断 vs 被通知直接读到，是两个不同性质的证据）。需要改的是**取值规则**，而取值规则必须在写入前锁定。

**重算代价（供未来评估）**：若迁移后才发现规则错，需要

```sql
-- 1) 改 source_type
UPDATE zhuli_memory_source SET source_type = <新值> WHERE ...;
-- 2) 重算 independent_key（有 ref / 无 ref 两分支）
UPDATE zhuli_memory_source
SET independent_key = CASE WHEN ref_id <> '' THEN source_type || '|' || ref_table || '|' || ref_id
                           ELSE source_type || '|-|' || content_hash END;
-- 3) 重算 item 的派生计数（按 evidence 聚合，不能用旧值累加）
UPDATE zhuli_memory_item SET times_reinforced = (
  SELECT MAX(0, COUNT(DISTINCT s.independent_key) - 1)
  FROM zhuli_memory_evidence e JOIN zhuli_memory_source s ON s.id = e.source_id
  WHERE e.memory_id = zhuli_memory_item.id
);
```

第二步会**改变 `idx_ms_dedupe` 的唯一性判断**：原本分属两个 `source_type` 的行可能变成同键 → 需要先合并（保留哪一行、evidence 如何改指）再建索引。这就是"规则必须在编码前锁定"的全部理由。

## 7. B-4.5 确定性与可审计性

### 7.1 映射的确定性

| 输入 | 是否静态 | 说明 |
|---|---|---|
| `zhuli_fact.source_type` | ✅ | 表内列 |
| `zhuli_fact.source_id` | ✅ | 表内列 |
| `zhuli_fact.source_text` | ✅ | 表内列（用于纠正前缀判定） |
| `inbox.source` | ✅（迁移事务内） | `onUpgrade` 的 T0 持写锁，通知监听器的写入会被阻塞；事务内读到的是稳定快照 |
| 迁移时间 `now` | ⚠️ **必须由参数注入** | 迁移函数签名应为 `migrate(db, now: Long)`（v4.2.1 行 3571 已是此写法）；**函数体内不得 `System.currentTimeMillis()`** |

## 8. 最终迁移映射伪代码

```kotlin
// 前置：sidRaw 来自 zhuli_fact.source_id；legacyRaw 来自 zhuli_fact.source_type
// carrierOf(sid) 只读：SELECT source FROM inbox WHERE id = sid

val legacy = legacyRaw?.trim().orEmpty()
val sid    = sidRaw
val carrier = if (sid > 0) carrierOf(sid)?.trim()?.lowercase() else null   // null = 行不存在
val hasRow  = carrier != null

// ── 步 1/2：断言模式优先（模式不是载体） ───────────────────────
val byMode = when (legacy) {
    "INFERRED" -> "MODEL_INFERENCE"
    "SYSTEM"   -> "AGENT_TASK"
    else       -> null
}

// ── 步 3：用户纠正（与 C0.2 §8.3 的 basis 判定同条件） ──────────
val isCorrection = legacy == "USER" && sourceText.startsWith("用户纠正：")

// ── 步 4：载体（仅 USER/INBOX 且确有行） ───────────────────────
val byCarrier = if (hasRow) when (carrier) {
    "notification" -> "INBOX_NOTIFICATION"
    "chat"         -> "CHAT_MESSAGE"
    "share", "link"-> "INBOX_SHARE"
    "sms"          -> "INBOX_SMS"
    else           -> null                      // 未知载体 → 计 unknown_carrier
} else null

// ── 最终取值 ───────────────────────────────────────────────────
val newType = when {
    byMode != null       -> byMode
    isCorrection         -> "USER_CONFIRMATION"
    byCarrier != null    -> byCarrier
    legacy == "USER"     -> "USER_MESSAGE"
    legacy == "INBOX"    -> "INBOX_NOTIFICATION"
    else                 -> "INBOX_NOTIFICATION"      // 未知旧值：最低档 + 留痕
}

// ── 引用三元组 ─────────────────────────────────────────────────
val hasRef   = sid > 0
val refTable = if (hasRef) "inbox" else ""
val refId    = if (hasRef) sid.toString() else ""
val refSubId = ""

// ── 独立性键 ───────────────────────────────────────────────────
val independentKey =
    if (hasRef) "$newType|inbox|$refId" else "$newType|-|$contentHash"

// ── 记账（全部计数，不静默） ───────────────────────────────────
//  mapped_carrier / mapped_mode / mapped_legacy / user_confirmation
//  default_mapping / dangling_ref / invalid_source_id
//  unknown_carrier / unknown_source_type
//  payload_json 追加（仅异常行）：
//    legacy_source_type  ← legacyRaw（当 unknown_source_type）
//    legacy_source_id    ← sidRaw（当 sid < 0）
//  ref 判定：hasRef && !hasRow → dangling_ref++
```

**三条实现纪律**：

1. `carrierOf` 只查一次并缓存（同一 `sid` 会被多条 fact 引用，重复查询会把 2 万行变成 4 万次查询）；
2. 所有 `when` 必须有 `else`，且 `else` 不留空——未知值不能落进 `null` 后崩掉整批；
3. 计数在**同一事务**内累加，迁移失败时随回滚一起丢弃，不写"半套统计"。

## 10. 结论

### 10.1 十项裁定

见 §0 的答案表。核心三句：

1. **B-2 A′ 通过**（补 `> 0` 判定）；
