## 1. 任务页 / 控制台入口根因分析（任务①）

**结论：`Screen.ZhuliHome` 与 `Screen.ZhuliTasks` 在当前 UI 中一直是可达的，代码无缺陷。批次 B 验收报告中的 C-3 是验收操作误判。**

排查过程（先查代码、再上设备实证，未猜测）：

1. 代码层：`RouteActivity.kt` 中两条路由均有注册（`composable<Screen.ZhuliHome>` → `ZhuliHomeScreen`，`composable<Screen.ZhuliTasks>` → `ZhuliTaskScreen`）；入口存在于两处——`SettingPage.kt`（"zhuli 助理" 分组 → "zhuli 控制台"）与 `ChatDrawer.kt`（底部操作行 `DrawerAction`，Shield 图标）。两处均为无条件渲染，自初始快照提交 `c44314b` 起就存在。
2. 设备实证（雷电模拟器，uiautomator dump + 实点验证）：
   - 抽屉底部操作行有 4 个可点击元素。**宽 191px、带 'zhuli' 文字的是"当前助手选择 pill"**（点击弹出助手选择面板——这正是验收时点到的元素，因此误判为"入口不可达"）；
   - **真正的控制台入口是旁边 72×72 的盾牌图标按钮**（无文字标签）。实测点击 → 正确进入 "zhuli 控制台"（`Screen.ZhuliHome`）；
   - 控制台首屏没有"任务"卡片，**下滑后可见"任务 / 多步骤执行记录与待确认操作"卡片**，点击 → 正确进入任务页（`Screen.ZhuliTasks`），页内含"发起一个任务"输入框、执行按钮与任务列表。
3. 判定：无需"恢复入口"的修改。验收失败的根因是：①把助手 pill 误认为入口按钮；②控制台"任务"卡片在首屏之下未滚动查看。

**入口链路（前后对比）**：与验收时完全一致，无代码改动——

  [zhuli 助手 pill] [盾牌图标 → Screen.ZhuliHome] [齿轮 → Screen.Setting] …

## 2. Debug 专用测试钩子（任务②）

**新增文件（只在 `app/src/debug/`，Release 不参与编译）**：

| 文件 | 内容 |
|---|---|
| `app/src/debug/AndroidManifest.xml` | 声明 `AgentTestReceiver`（action `com.zhuli.debug.TEST`） |
| `app/src/debug/java/com/zhuli/debug/AgentTestHarness.kt` | 脚本化模型后端 `ScriptedTestProvider`、4 个 Mock 工具、12 个场景剧本、广播接收器（命令：setup/run/approve/deny/pause/resume/cancel/status） |

**main 侧挂载点（3 个文件的最小改动，Release 下零调用方）**：

- `Gateway.kt`：`ModelRouter.registerProviderForTest()` —— 测试后端与生产后端走同一路由规则；
- `Policy.kt`：`ToolRegistry.registerToolForTest()` —— Mock 工具与真实工具同走 policy/审批，无旁路；
- `ZhuliAgentRuntime.kt`：`registerTestProvider/registerTestTool` + `isInitialized`。

**约束达成**：

- 结果全部来自真实 `ZhuliAgentRuntime.loop()`（共享实例）：同一个 `PolicyEngine`、同一个 `SqlAgentStore`、同一套审批状态机与 `AgentCoordinator` 并发锁；
- Mock 工具只有四种：只读回显 `test_read`、写本地（走 ASK 审批）`test_note`、必败 `test_boom`、可配时长的慢工具 `test_slow`，均不触碰真实用户数据；
- 脚本后端按请求 tag（taskId 前 8 位）分流剧本，多任务并发互不串线；
- 使用方式：`adb shell am broadcast -a com.zhuli.debug.TEST --es cmd run --es scenario <名> -n <pkg>/com.zhuli.debug.AgentTestReceiver`。**必须显式指定组件**：Android 14 会以 "Background execution not allowed" 拦截隐式广播（本次实测踩到，`dumpsys activity broadcasts` 中可见 skip 记录）。

**过程中发现并修复的真实生产缺陷（B 类）**：`AgentLoop` 步数上限暂停后**恢复永远无法推进**——旧实现拿任务终身步数当"单次"预算判断，每次 resume 只在循环顶部追加一条 NOTE，预算永不重置，任务卡死在 PAUSED 直到撞 `hardStepCap=24` 变 FAILED。`RunOutcome.Paused` 的文档承诺"可以继续"实际做不到。修复：`maxSteps` 改为按"本次运行新增步数"计算（每次恢复重新领预算），`hardStepCap` 保持终身口径兜底防跑飞。新增 JVM 回归测试 `步数上限暂停后恢复能继续推进并完成`（断言每次 resume 步数必须增长、最终 DONE、总步数 < 24）。该缺陷由本次 C 场景外的 A2 场景在设备上首次暴露（超限收尾步被上限拦截）。

4. **G 场景只验证了"无本地模型时 fail-closed"**：真实端侧模型（LiteRtLocal）装好后的"严格 local-only 推理"仍未验证（模拟器无本地模型资产）。
