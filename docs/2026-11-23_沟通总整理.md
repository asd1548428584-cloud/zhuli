## 1. 项目定位与最终目标

zhuli 是一个个人自用的原生 Android
个人助理，目标不是做一个普通聊天客户端，也不是简单的通知收集器，而是逐步成为用户授权下的个人信息、生活与工作中枢。

### 1.1 核心职责

-   **理解状态：**
    持续理解用户的生活、工作、日程、近期关注事项和正在推进的项目。
-   **采集信息：** 在 Android
    权限和系统能力允许、且用户授权的范围内，主动接收手机信息；同时接收用户主动分享的文字、图片、文件、链接、语音转写等内容。
-   **先保存、后理解：** 原始信息先可靠地本地保存，再由 AI
    异步整理、提取和归档。不能要求用户把每条通知或信息手动转发给 zhuli。
-   **形成长期记忆：**
    将原始材料整理为事件、事实、人物、项目、偏好、任务和关系，并保留来源、时间、置信度和修订历史。
-   **主动发现：**
    识别待办、风险、遗漏、重复事项、生活规律变化和可改进的问题，主动提醒或提出计划。
-   **执行事务：**
    在授权范围内调用手机系统能力或应用工具，完成低风险、可撤销的内部事务。
-   **持续反馈：**
    通过每日简报、每周总结、任务进展和必要的异常提醒，让用户知道系统发现了什么、做了什么、为什么这么做。

### 1.2 产品形态

采用两个相互独立、职责明确的工作界面：

1.  **主助理界面**
    -   面向日常交流、询问、计划、任务、简报和主动提醒。
    -   主要使用云端
        API，处理复杂推理、跨主题分析和需要较强模型能力的任务。
    -   共享统一的记忆、任务、工具、权限和执行记录。
2.  **本地信息处理工作台**
    -   面向本地数据查看、整理、分类、隐私处理、模型选择和处理队列。
    -   使用本地模型完成离线、隐私敏感或适合本地完成的任务。
    -   能查看原始信息、处理状态、AI 提取结果、来源关联和用户修正记录。
    -   不应做成另一个与主助理割裂的聊天应用。

两个界面不是两套产品内核。它们共享同一套数据层、记忆系统、任务系统、权限体系、工具注册表和执行日志。

## 2. 两天讨论的关键决策与路线变化

本节专门防止后续 AI 把早期讨论中的临时方向当成最终决定。

### 2.1 关于底座：最终以旧 zhuli 为主体

讨论早期曾把 Agro 作为候选新底座，原因是它的工程结构相对清晰，并包含
KMP/Compose、本地推理和 Agent Loop 等可研究内容。

随后用户明确纠正了方向：**不要另起炉灶，继续在用户自己的 GitHub zhuli
仓库基础上改造。** 这是当前最高优先级的有效决策。

执行要求： - 不把 Agro 直接替换为 zhuli 的主体工程。 - 不把旧 zhuli
仅当作一个 Android 技术资产包。 - 不整体回退或推翻旧 zhuli
的业务代码。 -
先确认现有模块的真实状态、依赖关系和测试情况，再决定保留、拆分、替换或重写。 -
对旧项目中的上游框架代码和自研代码做清晰区分，避免为了"清理架构"而误删已可用的业务能力。

### 2.2 Agro 的定位：参考项目，不是主仓库

Agro 仓库：`https://github.com/Onion99/Agro`

可以重点参考： - KMP/Compose 的工程组织方式（是否适合当前原生 Android
项目，要以成本和收益评估）。 - LiteRT-LM 的本地推理集成思路。 - Agent
Loop 的运行流程、工具调用循环和结构化结果处理。 -
模型与推理运行时的抽象边界。

不能直接假定 Agro 已经具备完整个人助理能力。已有审计材料指出： -
真实注册的 Agent 工具数量很少，主要为 `AnalyzeUrlTool` 和
`SearchWebTool`。 - MCP、Skills、Intent
等部分没有真正接入实际系统，不能把占位代码当成可用功能。 - Agro 并未提供
zhuli
所需的完整个人长期记忆、人物/项目档案、任务体系、主动助理、健康生活管理、手机数据接入和安全数据治理。 -
所以 Agro 是局部技术参考，而不是"拿来就能用"的完整助理底座。

### 2.3 双通道 AI：云端 API + 本地模型

目标是混合架构，不是二选一。

**云端通道：** -
负责主助理日常对话、复杂推理、长链路任务、跨主题归纳和高质量规划。 -
通过统一的 Cloud Gateway 接入不同 API 服务商。 -
不允许业务模块直接绑定某一家模型 API。

**本地通道：** -
负责离线处理、隐私敏感数据的初步理解、分类、脱敏、轻量抽取和本地工作台任务。 -
在网络不可用时，仍应能完成部分基础处理。 -
本地模型不应被强行要求承担其能力范围之外的复杂推理。

**调度原则：** - 原始信息接收后，先本地可靠落库。 -
本地优先完成轻量预处理、敏感信息识别和可本地完成的任务。 -
需要更强模型时，经过隐私策略和授权判断，再调用云端 API。 -
可配置异步批处理周期。早期讨论过约半小时/一小时处理，后续方案可将其设计为可配置队列周期（例如
1--2 小时），但具体默认值仍需通过实际使用验证。 -
重要事件、紧急提醒不能机械等待批处理周期，应有独立的实时处理通道。 -
云端和本地模型必须共享统一的任务输入输出协议、记忆访问策略和执行权限规则。

### 2.4 自主执行权限边界

用户接受"自主助理"定位，但不意味着模型可以不受限制地操作手机。

-   低风险、可撤销的内部操作：在预先授权范围内可自主执行，例如内部归档、分类、整理、生成草稿、建立内部待办等。
-   涉及对外承诺、对外发送、财产损失、隐私扩散、不可逆后果或高风险操作：执行前必须向用户征求明确同意。
-   创建或修改手机日历、提醒等系统数据，需要尊重用户设定的权限范围；对具体写入动作的授权边界应在权限模型中明确。
-   每次工具执行都应记录：触发来源、模型判断、使用的工具、参数摘要、权限依据、执行结果、失败原因和撤销方式（若可撤销）。
-   不允许模型通过提示词或工具参数绕过权限系统。

### 2.5 手机信息采集原则

用户希望 zhuli 在 Android
允许且用户授权的范围内，尽可能充分地获取手机信息，而不是只依赖用户主动转发。

潜在数据类别包括： - 通知； - 短信； -
通话记录及用户明确允许的相关信息； - 联系人； - 原生日历和提醒； -
位置； - 健康与活动数据； - 图片、文件和用户分享的材料； -
录音转写文字； - 应用使用上下文（需评估系统权限、隐私和实现可行性）。

必须遵守： - 每一类数据都要有独立权限开关、用途说明和数据保留策略。 -
Android 系统版本、厂商
ROM、应用商店政策和权限限制会影响实际能力，不能把"理论上可获取"写成"已经实现"。 -
用户撤销权限后，系统应停止采集，并明确处理已存数据的规则。 -
原始信息先落本地，再异步理解；不得因云端不可用而丢失原始输入。

### 2.6 电话录音与转写

用户在 11 月 22 日明确了边界： - 录音仅考虑**双人电话**场景。 -
原始录音不由 zhuli 长期保存。 - 长期保存的是转写后的文字。 -
多人通话/多人会议不在当前这条录音能力的默认范围内，需另行讨论。 -
具体实现必须先核实 Android
版本、设备厂商策略、当地法律和系统权限限制；不得承诺所有手机都能通过普通应用直接录制通话。

### 2.7 日历与提醒

用户明确倾向： - 日历事件写入手机原生日历。 -
提醒使用手机原生提醒能力/已设置的原生提醒体系。 - zhuli
需要负责解析、组织、提醒逻辑和状态管理，而不是另造一套与系统日历完全割裂的日历。 -
写入前后的授权、重复检测、失败反馈、更新和撤销机制必须设计清楚。

## 3. 目标设备与开发环境

### 3.1 最终目标手机

-   设备：努比亚 Z70 Ultra
-   型号：NX733J
-   SoC：Qualcomm Snapdragon 8 Elite
-   芯片代号：SM8750
-   系统：Android 16 / API 36
-   ROM：星云 OS 2.0.14MR2
-   架构：ARM64
-   需要重点验证：16KB 内存页兼容性、原生库 ABI、LiteRT-LM

以上设备信息来自项目讨论和既有选型报告；真机验收时仍须通过系统属性和实际运行环境重新读取，不能只依赖文档。

### 3.2 雷电模拟器先行策略

用户明确要求先用雷电模拟器完成开发和测试。模拟器是开发主环境，不是临时演示工具。

至少规划三个实例：

-   **LD-01 主测试实例：** 用于日常开发、安装、升级和主要功能回归。
-   **LD-02 干净环境实例：**
    用于首次安装、权限流程、无历史数据、迁移和恢复测试。
-   **LD-03 异常环境实例：** 用于断网、权限撤销、进程被杀、存储不足、API
    失败、后台限制等异常测试。

实例的 Android 版本、API
Level、ABI、分辨率、CPU/内存配置必须实际探测并记录，不能把某个版本写死为雷电必然配置。

雷电官方资料表明可通过 ADB 和 `ldconsole`
管理实例。常用命令示例（包名和设备序列号需以实际项目为准）：

``` powershell
adb devices
adb -s emulator-5554 shell getprop ro.build.version.sdk
adb -s emulator-5554 shell getprop ro.product.cpu.abi
adb -s emulator-5554 install -r zhuli-debug.apk
adb -s emulator-5554 shell monkey -p <实际包名> 1
adb -s emulator-5554 logcat -d > test-log.txt
```

多实例时必须用 `adb -s <serial>` 明确指定目标设备，不能依赖默认设备。

### 3.3 模拟器能力边界

雷电通过不等于目标手机通过。尤其不能在模拟器上最终证明： - Snapdragon 8
Elite 的真实 GPU/NPU 性能； - 真实功耗、发热和温控； - 星云 OS
的后台冻结、进程保活与自启动策略； - ARM64 Native
库在目标系统上的全部兼容性； - 目标设备的 16KB 页兼容性； -
真实电话录音、厂商通知机制、Health Connect 和定位表现。

如果雷电实例是 x86_64，则它不能直接证明 ARM64
原生库可运行；本地推理运行时需要先检查 ABI 支持。真机阶段再做
ARM64、16KB 页和硬件加速专项测试。

数据迁移、恢复演练和备份完整性需要真实执行验证。

### 4.5 审计结论的正确解读

旧 zhuli
有可复用的业务资产，但其上游框架代码规模远大于自研部分；这意味着重构时必须控制边界，避免把大量上游代码当作用户独有资产。正确做法是： 1.
识别上游框架与自研业务； 2. 保留许可证与来源信息； 3.
对自研业务建立模块级测试； 4. 将业务逻辑从 UI 和上游框架耦合中逐步拆出；
5. 通过接口隔离逐步替换底层实现，而不是一次性推倒重建。

│   ├── Context Builder
│   ├── Policy & Permission Engine
│   └── Proactive Assistant Scheduler
│
├── AI Gateway
│   ├── Cloud Gateway（多供应商 API）
│   ├── Local Gateway（本地模型）
│   ├── Model Router（按任务、隐私、网络和成本路由）

│   ├── Tool Registry

│   ├── Fact Store

### 5.1 数据处理主链路

推荐统一为：

``` text
RawItem → Event / Fact / Entity → Task / Reminder / Insight
```

-   `RawItem`：原始通知、短信、用户分享、文件、转写文本等。
-   `Event`：发生过的事情，包含时间、参与方、地点（若有）、来源。
-   `Fact`：较稳定的事实或偏好，需记录置信度和有效时间。
-   `Entity`：人物、组织、项目、地点、应用等对象。
-   `Task`：从信息中识别出的待办、计划、跟进或提醒。
-   `Insight`：跨时间、跨来源归纳出的趋势、风险或建议。

所有派生信息必须能回溯到来源 RawItem；AI
不能把推测写成确定事实。用户修正后应保留修订记录，避免下一次又恢复错误信息。

### 5.2 记忆分层

建议至少区分： - 原始资料层：未经 AI 改写的输入。 -
事件层：有时间和来源的事实性记录。 -
长期事实层：稳定偏好、长期约束、持续状态。 -
人物/项目档案层：关系、背景、进展、关联任务。 -
工作记忆层：当前对话和近期任务所需的临时上下文。 -
派生洞察层：趋势、风险、建议和总结。

必须有删除、纠正、过期、合并、冲突处理机制。不能把"曾经出现过"自动等同于"长期真实"。

## 6. 核心功能需求清单

### 6.1 信息接收与 Inbox

-   自动接收获准的通知、短信等系统事件。
-   接收用户通过 Android 分享菜单发送的文本、链接、图片和文件。
-   原始内容优先落本地数据库/文件存储。
-   保存来源应用、时间、接收方式、权限状态和处理状态。
-   去重、重复通知合并、噪声过滤。
-   异步处理队列，支持失败重试和人工重新处理。
-   本地工作台可查看原始内容及其 AI 处理结果。

### 6.2 隐私与安全

-   每个数据来源单独授权。
-   本地/云端处理路由可解释、可配置。
-   云端发送前进行敏感信息识别和脱敏。
-   用户可查看哪些内容曾发送到云端。
-   数据库、附件、缓存和备份采用一致的安全策略。
-   密钥由 Android Keystore
    等合适机制保护；需评估数据库加密方案和密钥恢复策略。
-   备份必须覆盖核心数据库和必要附件，并进行恢复演练。
-   日志不得泄漏短信、通知、联系人、令牌和 API Key 等敏感内容。

### 6.3 主助理与对话

-   多模型 API 配置与切换。
-   云端 API 统一接口，支持超时、重试、流式输出、错误归一化。
-   本地模型统一接口。
-   对话可引用记忆和任务，但需展示来源或依据。
-   支持工具调用，并在工具调用前经过权限判断。
-   对话中可创建任务、日程和提醒；执行结果可追踪。

### 6.4 本地信息工作台

-   原始信息列表、分类和搜索。
-   本地模型选择、运行状态和资源占用。
-   待处理队列、失败队列、重试。
-   脱敏前后对比和云端处理记录。
-   AI 提取的人物、项目、事实、事件和待办。
-   用户纠正、确认、合并和删除。
-   离线状态下可用的基本操作。

### 6.5 长期记忆与检索

-   人物档案、项目档案、事实和事件关联。
-   语义检索不能只使用字符哈希伪向量。
-   检索结果需带来源、时间和相关度。
-   处理相互矛盾的信息：新旧事实、不同来源和用户确认优先级。
-   支持记忆纠正、过期和删除。
-   记忆写入需区分用户明确陈述、系统观察和模型推断。

### 6.6 任务、日程与主动助理

-   从通知、短信、对话和分享材料中提取任务。
-   任务状态：待处理、进行中、等待他人、已完成、已取消等。
-   任务优先级和四象限管理。
-   截止时间、重复规则、提醒和延期。
-   与手机原生日历、提醒体系对接。
-   定期回顾未完成任务和即将到期事项。
-   主动提醒应控制频率，避免噪声轰炸。
-   对外执行前必须通过审批闸门。

### 6.7 健康与生活状态

-   在用户授权下整合步数、运动量、睡眠时长等趋势。
-   形成每日简报和每周报告。
-   识别连续睡眠不足、活动量明显下降或生活规律显著变化，并主动提醒。
-   可提出作息、通勤和运动建议，并结合日程制定计划。
-   不定位为医疗诊断系统，不替代医生或医疗建议。
-   访问能力以 Health Connect、设备和系统实际支持情况为准。

### 6.8 电话与沟通信息

-   当前明确的录音范围是双人电话。
-   不长期保存原始录音，长期保存转写文字。
-   多人通话/会议另行处理。
-   通话记录、联系人和短信访问须遵守 Android 权限、当地法律和用户授权。
-   无法实现的系统级能力必须明确说明，不得用虚假 UI 假装完成。

## 7. 分阶段开发路线（建议基线）

每个阶段都必须先分析，再改代码；不得一次性让代码代理重写整个工程。

### Phase 0：工程冻结与可复现构建

目标： - clone 用户 GitHub 仓库； - 记录远端 URL、分支、HEAD
commit、工作区状态； - 检查 JDK、Gradle、Android SDK、NDK、依赖仓库； -
在雷电主实例中安装当前基线 APK； - 执行当前已有测试并记录失败； -
导出依赖树、模块清单、包名、权限、Native 库 ABI； - 建立 Git
tag/分支和回滚方案。

交付： - 基线审计报告； - 可复现构建步骤； - 当前 APK； -
当前测试结果； - 雷电实例信息； - 风险清单。

### Phase 1：模块边界与资产整理

-   区分上游 LastChat 代码与自研 zhuli 代码。
-   为自研模块建立依赖图和调用链。
-   标注保留、重构、替换、删除候选。
-   先为核心自研逻辑补测试。
-   不改变用户可见功能，避免大范围回归。

### Phase 2：数据层与安全

-   设计数据模型和迁移策略。
-   数据库加密、附件加密、密钥管理。
-   备份/恢复完整覆盖核心数据。
-   做迁移、损坏、恢复、密钥丢失等测试。
-   修复日志泄漏和明文敏感数据问题。

### Phase 3：统一 AI Gateway

-   定义统一模型请求/响应协议。
-   云端 API 适配器。
-   本地模型适配器。
-   模型路由和隐私策略。
-   超时、重试、取消、流式响应和错误处理。
-   业务模块不得直接依赖具体模型供应商 SDK。

### Phase 4：Agent Runtime

-   Agent Loop。
-   Tool Registry。
-   Tool Schema 和参数校验。
-   权限策略与审批闸门。
-   工具执行日志。
-   超时、取消、重试和撤销。
-   先实现少量真实工具，禁止暴露未接通的占位工具。

### Phase 5：Memory

-   Raw Inbox。
-   Event / Fact / Entity。
-   人物和项目档案。
-   来源追踪、置信度、冲突处理。
-   语义检索。
-   用户纠错与删除。

### Phase 6：Task & Schedule

-   任务提取和状态管理。
-   优先级/四象限。
-   原生日历适配。
-   原生提醒适配。
-   重复任务、截止时间和提醒策略。
-   审批与撤销。

### Phase 7：Android 数据接入

-   通知、短信、日历、联系人等逐类接入。
-   位置、健康数据、文件/照片和分享入口。
-   每类数据独立权限、说明、开关和测试。
-   电话相关能力独立评估，不与普通通知能力混为一谈。
-   对每种来源做权限撤销和系统重启测试。

### Phase 8：主动助理

-   定期扫描任务和状态。
-   生成每日简报和每周总结。
-   识别遗漏、冲突和风险。
-   形成建议并区分"建议"与"已执行"。
-   低风险授权动作可执行；高风险动作先询问。

### Phase 9：本地推理

-   验证目标模型格式、量化方案和运行时。
-   在雷电环境先验证可用性和功能正确性。
-   对 CPU/GPU/NNAPI 等路径做能力探测，不预设必然可用。
-   评估模型加载、内存、上下文长度、耗时和异常恢复。
-   真正硬件加速性能留到 Z70 Ultra 阶段。

### Phase 10：双工作界面与交互体验

-   主助理界面。
-   本地信息处理工作台。
-   统一导航、任务状态和记忆引用。
-   权限管理、数据管理、执行记录和模型设置。
-   不为了 UI 漂亮而提前牺牲核心数据和权限架构。

### Phase 11：雷电模拟器完整回归

至少覆盖： - 全新安装、升级安装、卸载重装； -
数据库迁移、加密、备份、恢复； - API
正常、超时、断网、限流、无效密钥； -
本地模型不可用、模型加载失败、内存不足； - 通知/SMS
接收、重复、去重、权限撤销； - 任务提取、提醒、日历写入和撤销； - Agent
工具成功、失败、超时、越权拦截； - 记忆来源、冲突、纠错和删除； -
后台运行、进程被杀、重启恢复； - UI 自动化和长时间稳定性。

### Phase 12：Z70 Ultra 真机验收

只有 Phase 11 通过后才进入： - ARM64 原生库； - Android 16 / API 36； -
16KB 页兼容； - LiteRT-LM 真实设备推理； - GPU/NPU/NNAPI 路径； -
内存、功耗、温度和长时间运行； - 星云 OS 后台限制、通知、开机恢复； -
Health Connect、定位和真实系统权限； - 真实场景 24 小时以上稳定性。
