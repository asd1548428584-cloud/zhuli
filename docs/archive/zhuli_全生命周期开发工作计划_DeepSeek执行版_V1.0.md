# 0. 给执行 AI 的最高优先级指令

你是本项目的技术负责人、架构师、Android 开发者、AI 工程师、测试工程师和项目管理者。你的工作不是机械照文档写代码，而是理解目标、审计现状、研究技术、制定项目专属路线、分阶段实施、验证结果，并依据用户反馈和真实测试持续调整。

## 0.1 不可违反的原则

1. **先审计后修改**：第一个阶段只允许只读检查。未完成审计、备份和风险说明前，不得修改代码、数据库、系统设置或设备权限。
2. **现有成果优先**：不得因偏好某种架构就推倒重写。先判断现有实现质量、复用价值、问题和迁移成本。
3. **事实与推测分开**：设备服务存在不代表第三方可调用；权限已授予不代表功能可靠；编译成功不代表真机可用。
4. **本地优先、隐私优先**：能在本地完成的任务优先本地完成；云端调用必须经过数据分级、脱敏、授权和出网留档。
5. **标准 API 优先**：优先 Android 官方公开 API、公开 SDK 和可维护的开源项目。厂商私有接口须确认合法开放、权限可用、维护可持续后才考虑。
6. **小步实施、及时验证**：一次聚焦少量相关改动，建立基线、修改、测试、回归；避免一次性大改多个模块。
7. **测试贯穿全程**：每个功能在设计时就要有测试方法，开发中持续验证，阶段结束时回归。
8. **真实设备优先**：后台、通知、闹钟、定位、健康、无障碍、屏幕捕获和耗电必须在目标手机验证。
9. **人保留最终决定权**：产品方向、重大架构变化、数据迁移、破坏性操作、权限扩大、对外发送数据等必须先说明并获用户确认。
10. **不虚报完成**：区分代码完成、编译通过、自动化测试通过、真机通过、长期稳定通过。
11. **文档持续更新**：需求、架构、接口、决策、测试、问题、版本和当前进度都要记录。
12. **控制上下文成本**：每次先读项目状态和当前步骤，再按需读取相关资料，不要每次重读全部文档。

# 1. 项目目标与产品边界

## 1.1 产品定位

zhuli 是面向单一用户、以 Android 手机为主要载体的个人 AI 助理。它不是普通聊天机器人，也不是简单待办 App，而是逐步成为能够：

- 接收用户主动分享的信息和经过授权的手机数据；
- 识别、分类、提取、关联和保存信息；
- 建立长期、可检索、可修正的个人记忆；
- 理解用户的工作、生活安排和上下文；
- 主动发现需要提醒、跟进或整理的事项；
- 通过对话查询资料、创建任务、设置提醒和调用工具；
- 在明确授权和安全边界内协助操作手机；
- 结合本地与云端模型，在能力、隐私、速度和成本间取舍。

最终目标是一个能长期陪伴用户、逐渐理解其工作和生活的个人助理，而不是堆砌 AI 功能的演示 App。

## 1.2 产品原则

### 本地优先
原始个人数据默认保存在手机；规则明确的任务优先本地代码；本地模型适合的任务优先本地推理；云端模型用于本地能力不足或用户明确要求的场景。

### 用户控制数据
用户能知道数据来源、存储位置、处理方式；数据可查看、修改、删除、导出、备份；可撤销授权和关闭数据来源；私人工作生活记录不得擅自用于无关任务或上传。

### 规则与模型分工
规则引擎负责确定性强、可验证、低成本的处理；模型负责语义理解、复杂表达、推理、总结和工具选择。模型输出必须经过结构校验、权限校验和业务校验。

### 只收不擅自发
不自动代用户发送消息、付款、发布内容或执行不可逆操作。手机自动化以“用户确认后执行单步操作”为基础。高风险操作必须二次确认。

### 可解释、可追溯
每条提醒能追溯来源；每次云端请求保留必要的脱敏出网记录；自动化操作记录授权、目标和结果；重要推断区分事实、模型推断和待确认。

## 1.3 当前功能范围（必须审计，不得直接视为已完成）

| 能力域 | 已知功能/方向 | 后续重点 |
|---|---|---|
| 输入 | 通知、分享、链接、图片、语音/视频、短信 | 稳定性、来源管理 |
| 理解 | 规则分类、时间/金额、快递、周期、模型调用 | 准确率、置信度、纠错 |
| 记忆 | SQLite、全文/向量检索、账本、聊天、提醒 | 加密、长期记忆质量 |
| 主动提醒 | 准点/周期提醒、简报、位置提醒 | 后台可靠性、误报 |
| 对话 | 查记忆、待办、账本、快递、建提醒、备忘 | 工具可靠性和上下文 |
| 手机操作 | 日历、小组件、快捷指令、单步点击 | 安全边界和失败恢复 |
| 隐私 | 敏感闸门、出网留档、Key 加密、备份导出 | 整库加密和权限分级 |
| 本地 AI | 规则、OCR 等 | 本地 LLM、Embedding、ASR |
| 云端 AI | OpenAI 兼容端点 | 多模型路由和成本控制 |

# 6. 阶段 1：产品需求与场景梳理

不要先堆功能，先围绕真实生活场景梳理端到端流程，例如：

- 通知中出现会议、截止日期和待办；
- 快递通知提取取件信息并提醒；
- 分享文字、图片、链接或文件并记住；
- 记录账目并查询周期支出；
- 查询过去提过的人、地点、任务和事件；
- 生成晨间/晚间简报；
- 识别周期事务和未完成事项；
- 根据位置和时间提醒；
- 自然语言查询、修改和创建任务；
- 请求助理执行手机操作；
- 查看、纠正、删除或导出记忆。

每个场景写明：触发条件、来源、授权、敏感级别、解析内容、工具、输出、失败处理、提醒方式和验证方法。

按用户价值、频率、技术难度、后台依赖、隐私风险和维护成本划分 P0/P1/P2：
- P0：核心链路可靠性、数据安全、记忆正确性、提醒可靠性、工具调用安全；

# 8. 阶段 3：总体架构与数据设计

建议至少划分：

1. 输入层：通知、分享、文件、链接、图片、音频、位置、健康、手动输入；
2. 接入适配层；
3. 解析层：规则、OCR、时间金额、分类、模型；
4. 标准化层：统一对象、来源、时间、置信度、敏感级别；
5. 存储层：原始收件、事件、记忆、提醒、账本、会话、出网记录；
6. 检索层：SQL、全文、向量、混合排序；
7. Agent 层：上下文、意图、计划、工具选择；
8. 工具层：查询、创建、更新、提醒、日历、账本、系统操作；

- UI 不直接操作数据库；
- 模型不直接拼 SQL；
- 模型不直接访问系统权限；
- 模型不直接执行未经校验的任意命令；
- 工具统一注册、参数校验、权限校验和审计；
- 原始输入不可被解析结果覆盖；
- 后台任务可恢复、可去重、可观察。

数据模型需审查并逐步覆盖 Inbox、Source、Event、Memory、Task、Reminder、Recurrence、Ledger、Parcel、Conversation、Message、Embedding、ToolExecution、Consent、EgressLog、Job 和迁移版本。

长期记忆尽可能保存唯一 ID、内容、类型、来源、创建/发生/更新时间、可信度、推断标记、敏感级别、用户确认、过期/更正状态和 Embedding 模型版本。

交付：总体架构、模块依赖图、数据模型/ER 图、数据流和权限流、工具接口规范、错误码规范、ADR。

# 10. 阶段 5：数据与隐私基础

## 10.1 数据分级
至少区分公开/低敏、普通个人数据、敏感个人数据、禁止出网数据。私人工作记录、位置轨迹、健康信息、消费记录和私人聊天应按敏感数据处理。密码、验证码、完整证件号、银行卡号和认证凭据禁止出网。具体分类由用户确认，不能只靠模型判断。

## 10.2 云端请求闸门
每次云端调用前：
1. 判断是否真的需要云端；
2. 尽可能本地处理；
3. 数据分级；
4. 移除不必要上下文；
5. 脱敏；
6. 禁止出网内容拦截；
7. 按授权策略决定是否允许；
8. 记录脱敏摘要、模型、时间、用途和结果；
9. 提供出网记录查看；
10. 失败时不得自动改用未授权服务。

## 10.3 数据库加密
项目介绍指出数据库文件仍为明文，应研究 SQLCipher 等方案。验证现有数据库迁移、密钥生成和 Keystore、密钥丢失、备份恢复、版本升级、性能、断电恢复和导出迁移。未备份、未验证迁移和恢复前，禁止直接对真实数据库加密或迁移。

验收：未授权敏感数据不能出网；禁止出网数据稳定拦截；Key 不明文落盘或入日志；备份可恢复；错误密钥不破坏原数据；删除、导出、撤权符合约定；云端调用可追溯。

# 12. 阶段 7：理解、分类与长期记忆

规则通道处理时间、日期、周期、金额、快递码、明确分类、模板、去重和标准化。模型通道处理复杂自然语言、含糊表达、语义分类、摘要、关系提取、意图和复杂问题。

模型输出必须经过 Schema 和业务校验。

记忆需区分原始资料、事件、任务、稳定事实、偏好、人物关系、地点、周期习惯、临时上下文、用户明确要求记住的内容和模型推断候选。不是每条输入都自动写长期记忆；保留来源；推断标置信度；冲突不擅自覆盖；用户纠正优先；允许过期、编辑、删除和导出；检索返回来源证据。

建立固定评测集，覆盖精确事实、时间范围、多条汇总、同名消歧、新旧冲突、纠正后查询、不存在信息、低置信推断、敏感权限和长跨度记忆。指标至少包括正确率、召回率、来源可追溯率、错误记忆率、无依据回答率、延迟和成本。没有依据时必须允许回答“不确定/没有找到”。

# 13. 阶段 8：AI Agent 与工具系统

Agent 负责理解请求、组织上下文、提出计划；工具服务负责在权限边界内执行。

```text
用户输入
→ 意图识别
→ 上下文/记忆检索
→ 敏感级别判断
→ 工具计划
→ Schema 校验
→ 权限/确认校验
→ 工具执行
→ 结果校验
→ 审计
→ 组织回答
```

每个工具定义唯一名称、用途、参数/返回 Schema、权限、敏感级别、是否确认、超时、重试、幂等、错误码、审计字段和测试。

删除/批量修改、对外发送、付款交易、修改系统权限、持续位置/录音/屏幕捕获、不可逆操作、上传敏感内容必须明确确认。

测试工具选择、参数、缺参追问、失败解释、结果真实性、越权拦截、重复调用幂等、多工具顺序、失败恢复和异常参数拦截。

# 14. 阶段 9：主动任务、提醒与后台可靠性

任务类型：一次性、周期、截止日期、待办跟进、快递、位置触发、晨间简报、晚间回顾、失败重试、待确认建议。

调度原则：
- AlarmManager 用于真正需要准点的任务；
- WorkManager 用于可延迟、可约束、可重试工作；
- FGS 仅用于符合 Android 规定且用户可感知的持续任务；
- FCM 可作合适场景的补充，不保证所有本地任务；
- 重启恢复任务；
- 时区、时间、权限变化时重新计算；
- 任务有唯一 ID、状态、下次时间和幂等标识；
- 重复触发不得重复提醒；
- 完成、稍后、取消、撤回状态一致。

星云 OS 专项测试：熄屏 1/4/8/24 小时、前后台、最近任务划掉、省电模式、网络切换、进程被杀、重启、升级、自启动开关、电池白名单、FGS 类型、精确闹钟权限、通知权限。记录触发时间、误差、进程状态、系统状态和耗电；单次成功不代表长期可靠。

# 15. 阶段 10：本地 AI 与云端协同

建立统一模型服务层，业务模块不得直接绑定某家模型 API。

路由可选规则、本地轻量模型、本地较大模型、云端模型或用户确认后云端模型，依据任务、敏感级别、能力、成本和设备状态决定。

手机端先做最小 Demo，测模型加载、NPU/GPU/CPU、首 token、生成速度、内存峰值、发热、耗电、稳定性、模型体积和恢复能力。不能仅凭规格表认定可用。

云端评估 Tool Calling、JSON 稳定性、中文、长上下文、速度、价格、限流、可用性、数据政策和失败重试。不得自动把敏感请求切换到另一云服务。

交付：模型服务抽象规范、本地模型评测、云端模型评测、路由策略、隐私与降级策略。

# 16. 阶段 11：手机操作与系统集成

能力优先级：
1. 公开 Android API；
2. 官方 Provider；
3. Intent / Deep Link；
4. 通知操作；
5. 分享和系统选择器；
6. 用户明确授权的 AccessibilityService；
7. 确认开放后才考虑厂商能力。

自动化要求：操作前说明目标；高风险确认；只执行当前确认的单步；不盲点、不连续盲点；检查目标窗口和控件；操作后检查结果；无法确认时停止；不绕过银行、支付、验证码和安全验证；失败提供手动路径。

验收：用户确认后执行、目标正确、失败可停止、无重复点击、无跨 App 误操作、有记录、ROM 拦截可降级、用户可关闭。

# 17. 阶段 12：交互体验与日常工作流

# 19. 阶段 14：发布、观察与持续迭代

发布前检查版本号、变更日志、Release 构建、签名、权限说明、数据库迁移、备份恢复、核心测试、真机回归、崩溃、隐私、出网和回滚方案，最终由用户确认。

发布后观察崩溃、后台失败、提醒误差、通知漏收、重复数据、工具调用失败、云端失败、本地模型性能、耗电、纠错频率、检索失败和权限撤销。以本地诊断和用户主动提供日志为主，不默认上传个人数据。

迭代闭环：

```text
真实使用
→ 收集问题（用户反馈/本地日志/测试）
→ 分类：Bug / 体验 / 性能 / 安全 / 新需求
→ 评估严重程度和影响
→ 复现
→ 根因分析
→ 最小修改方案
→ 回归风险评估
→ 必要时用户确认
→ 实施
→ 单元/集成/真机回归
→ 更新版本和文档
→ 观察结果
```

不要为了修一个问题顺手重构整个模块。确需重构时，说明收益、风险、范围和回滚路径。

# 20. 中途修改、需求变化与架构调整

## 20.1 修改分级

**A 类：局部修复**  
例如解析 Bug、UI 显示、文案、模块内校验。分析、修改、测试、记录。

**B 类：模块级调整**  
例如更换模型、调度方式、数据适配器、记忆检索策略或增加工具。先说明现状问题和证据，比较方案，评估模块/数据/权限/性能/测试影响，说明迁移与回滚，获确认后实施并回归。

**C 类：系统级调整**  
例如数据库整体加密、大规模迁移、核心架构重构、更换推理运行时或 Agent 框架、改变数据出网策略、引入高敏感权限。必须形成专项方案和风险评估，经用户明确批准；先做独立 Demo 或迁移演练，禁止在唯一真实数据上试错。

## 20.2 每次修改必须回答

- 为什么改？证据是什么？
- 不改会怎样？
- 修改解决什么？
- 影响哪些模块？
- 是否影响数据库或用户数据？
- 是否增加权限、网络请求、耗电或内存？
- 是否引入新依赖？
- 如何测试？
- 如何回滚？
- 是否需要用户确认？

## 20.3 需求变化

用户改变想法时，先判断局部调整还是方向变化；保留仍有效的已确认需求；标记被替代的旧决策；评估对已完成模块的影响。不要为了旧计划拒绝合理变化，也不要把临时想法自动当正式需求。重大变化形成新版需求和路线图供用户确认。

高风险改动前确认备份存在且可读，尽可能在副本演练，明确回滚步骤，记录版本和数据库版本，并获得用户确认。

# 24. 项目完成的定义

1. 需求明确；
2. 架构和权限边界明确；
3. 实现完成；
4. 单元测试通过；
5. 集成测试通过；

7. 异常路径通过；
