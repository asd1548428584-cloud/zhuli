# 1. 产品定位与本周期总方针

## 1.1 定位（经用户与外部评审确认的方向）

**一个理解手机信息、替用户管理日常事务、能长期积累个人记忆的本地个人信息中枢**，不是功能越来越多的手机 AI 助手，也不是 AI 对话入口。

三件必须做到非常好的事（本周期一切工作围绕它们排序）：

| # | 核心承诺 | 对应能力 | 当前最大威胁 |
|---|---|---|---|
| 1 | **重要信息不会漏** | 通知/分享/短信采集完整性 | 敏感通知 ignore、无每 App 开关、噪声闸门误杀 |
| 2 | **该提醒的时候不会忘** | 提醒引擎 + 后台可靠性 | 星云 OS 冻结/查杀、重启广播被拦、误报损害信任 |
| 3 | **问过去的事真的找得到** | 全文 + 向量混合检索 | **FTS 索引恒空（已证实缺陷 D5）**、哈希伪向量非语义 |

## 1.2 本周期总方针：先打磨，后扩张

1. **功能冻结线**：阶段 A–E（§4）验收通过之前，不新增功能域。冻结期内只做：缺陷修复、可靠性加固、已实现功能的复验、体验打磨。本地语音运行时、skills 接线、真语义 Embedding、FGS/FCM 保活、群聊摘要等全部排在阶段 H，入场条件见 §4。
2. **区分"已实现 / 已验收 / 规划中"**：任何文档、面板、介绍不得把配置预留（ModelStore 目录）、死代码（skills 表）、伪实现（哈希向量）描述为已具备的能力。
3. **隐私优先于功能**：出网链路缺陷（D1–D4）是最高优先级，先于一切新功能，也先于数据库加密。
4. **提醒宁缺毋滥**：误报一次对信任的损害大于漏报一次。引入置信度三级机制（§6），低置信只存不提醒。
5. **数据安全第一操作**：任何可能影响装机/签名/数据库的操作之前，先完成阶段 A 的明文拉库备份。当前备份体系存在跨设备不可解的断链（D7），**明文拉库是目前唯一可靠的数据逃生通道**。

**C 类：明确未做**

- `embeddings`：FNV 哈希 1/2-gram → 256 维伪向量，代码注释自认"不是语义模型"（VectorSearch.kt:13,94-117）。

**暂缓（需求文档已定）**：剪贴板监听、TTS、CSV 批量导入、云备份/WebDAV。

# 6. 提醒置信度三级机制（设计口径，阈值待用户确认）

```text
提取结果
├─ 高置信：明确日期+时刻+事件结构完整（如"周三下午三点评审"解析出唯一未来时间）
│   → 自动建提醒（现有链路），通知里保留来源追溯
├─ 中置信：时间可解析但语义含糊（"下周给我""明天左右""月底前"）、
│   或分类置信度低、或来源为群聊转述
│   → 写入"待确认事项"，晨间简报/面板列出，用户一键确认后才建提醒
└─ 低置信：仅疑似时间词、无法确定未来性、噪声源
    → 只入库保存，不提醒、不打扰
```

配套要求：
- 每条提醒保留 `confidence` 与判定依据字段（库迁移随 T-E1 统筹，先加列）；
- 用户纠正（改时间/取消）回写为训练样本，定期回顾误报率；
- 待确认事项超过 N 天未处理自动降级为低置信归档，不堆积打扰；
- 验收口径：**误报（用户取消且标记"不该提醒"）率逐周下降；高置信通道准点率不回退**。
