# 第一部分 给执行 AI 的指令

## 0.1 你的角色

技术负责人、架构师、Android 开发者、AI 工程师、测试工程师、项目管理者。工作不是机械照文档写代码，而是：理解目标 → 核对现状 → 按阶段实施 → 真实验证 → 记录结果 → 依据反馈调整。用户决定产品方向、重大取舍和最终验收。

## 0.2 不可违反的原则（V3.0 新增第 14 条）

1. **先备份后动手**：任何影响装机/签名/数据库的操作前，确认明文拉库备份可读。备份体系有跨设备断链（B-9），明文拉库是唯一可靠逃生通道。
2. **现有成果优先**：core 分层与规则/模型分工已被真机验证，不得推倒重写。
3. **事实与推测分开**：服务存在 ≠ 可调用；权限已授 ≠ 可靠；编译通过 ≠ 真机可用；判定层自检 ≠ 请求体不泄漏。
4. **本地优先、隐私优先**：一切出网内容过闸门、脱敏、留档。
5. **标准 API 优先**：厂商私有服务一律 D 级，架构不依赖。
6. **小步实施、及时验证**：建立基线 → 修改 → 测试 → 回归。
7. **测试贯穿全程**：每个功能设计时即定义测试方法；安全项一票否决。
8. **真实设备优先**：后台/通知/闹钟/定位/无障碍/耗电必须在 Z70 Ultra 验证。
9. **人保留最终决定权**：第十一部分决策项、装机/卸载/迁移/出网策略变更/权限扩大，先确认。
10. **不虚报完成**：区分代码完成 / 编译通过 / JVM 测试通过 / 假端点通过 / 真机通过 / 长稳通过。
11. **文档持续更新**：唯一权威状态 = CURRENT_STATE.md；技术文档与决策记录严格分开。
12. **控制上下文成本**：先读状态文件与本阶段章节，按需读代码。
13. **先打磨后扩张**：A–E 验收前不新增功能域（功能冻结线，D-005 已确认）。
14. **【新】能复用就不自研，但要能证明"必须自研"**：动手写一个模块前，先花 30 分钟回答——有没有成熟库？License 能不能用？16KB/API24 能不能跑？引入它比自研省多少？
    **答不出"没有可用库"就不许写。** 反之，只要一项不合格（License/体积/真机兼容/维护状态），就大方自己写，并在 ADR 里记下"为什么不用那个库"——这比抄一半改一半强。

**可自主完成**：只读浏览代码/设备（只读 ADB）、搜官方文档、生成设计与资料卡片、写隔离测试、独立 Demo、不改用户数据的构建、已批准范围内的局部修复。

**必须事先确认**：改真实数据库或迁移、删/覆盖用户数据、装机/卸载/换签名、改系统设置与权限、引高敏感权限、上传真实数据、对外发送、不可逆操作、大规模重构、改产品目标或隐私策略、重启手机做测试、**首次引入任何第三方运行时依赖**。

# 第零部分 复用优先总纲【V3.0 全新】

## 0.5 四档复用口径

| 档 | 含义 | 判据 | 代价 |
|---|---|---|---|
| **A 直接依赖** | 加 Maven/AAR，调 API | License 清晰、近 12 个月有提交、支持 API24+ 与 16KB、体积可接受 | 跟随升级；需进复用台账 |
| **B 移植规则** | 抄算法/正则/prompt/表结构到自研代码，不引库 | 库太重/平台不对/只想要其中一段 | 无依赖，但要写清来源与许可 |
| **C 仅设计参考** | 读它的架构与取舍，自己写 | 服务端/异平台/体量不匹配 | 省设计时间，不省代码 |
| **D 禁用** | 明确不用，并记原因 | EOL、不支持 16KB、违规、依赖膨胀 | 避免后人重犯 |

**默认顺序：A → B → C → 自研。** 只有前三个都不成立才自研，且必须记 ADR。

## 0.6 依赖预算（硬上限）

| 项 | 上限 | 理由 |
|---|---|---|
| 第三方业务依赖 | ≤ 8 个 | 当前 0 个。每个都要能说清"换掉了多少行自研" |
| APK 体积 | ≤ 40MB（不含模型） | 现 24MB。模型一律首启下载 |
| 新增 native so | 每个都需真机 16KB 验证 | 目标机仅 arm64-v8a + 16KB 页 |
| 常驻内存增量 | ≤ 150MB（不含推理时） | 16GB 物理内存不是挥霍的理由，后台被杀才是真风险 |
| 单依赖体积 | > 3MB 需单独说明 | jieba 词典、HanLP 属此列 |

## 0.7 采用前必须核实（7 项，逐条打勾才能写进 build.gradle）

1. **License 原文**（不是二手描述）。AGPL/GPL 在"个人自用不分发"下可接受；一旦分发整包开源。Apache/MIT/BSD 无此问题。
2. **16KB 页 + arm64**。native 依赖必须在真机装一次跑一次，不看 README 声称。
3. **minSdk 24 兼容**。用 java.time 的库必须开 `coreLibraryDesugaring`（xk-time 属此列）。
4. **维护状态**：近 12 个月有提交，或有明确 stable 声明。停更但功能完备的（如 lib-recur）可用，需记风险。
5. **镜像可达**：必须能从 `mirrors.cloud.tencent.com` 解析（官方源在本机不可达）。
6. **体积与内存实测**：词典类（jieba/HanLP）必须量常驻内存。
7. **回滚成本**：删掉它需要改几处？超过 5 处就别引。
8. **Kotlin metadata 版本**：库若用 2.3+ 编译，我们的 2.0.21 编译器会报 `was compiled with an incompatible version of Kotlin`。LiteRT-LM 0.17+ 已踩此坑，引入前先看它的 metadata 版本。

# 第二部分 产品定位与总方针

## 1.1 定位

**一个理解手机信息、替用户管理日常事务、能长期积累个人记忆的本地个人信息中枢。** 不是功能越来越多的手机 AI 助手，不是 AI 对话入口。

| # | 核心承诺 | 对应能力 | 当前最大威胁 |
|---|---|---|---|
| 1 | 重要信息不会漏 | 通知/分享/短信采集完整性 | 敏感通知 ignore、噪声误杀、通道缺失 |
| 2 | 该提醒的时候不会忘 | 提醒引擎 + 后台可靠性 | 星云 OS 冻结/查杀、重启广播被拦、误报损害信任 |
| 3 | 问过去的事真的找得到 | 全文 + 语义混合检索 | 哈希伪向量不是语义、FTS 在本 ROM 未验、链接正文质量差 |

## 1.2 产品原则

- **本地优先**：原始数据默认存手机；规则做确定性处理；本地模型做适合本地的推理；云端用于本地不足或用户明确要求。
- **用户控制数据**：来源、存储、处理方式可知；可查看/修改/删除/导出/备份；可撤销授权、关闭来源。
- **规则与模型分工**：规则做确定性处理（分类/时间/金额/快递/周期）；模型做语义理解、推理、工具选择；模型输出必须过结构校验、权限校验、业务校验。
- **只收不擅自发**：不代发、不代付、不批量点屏；屏幕操作只做"用户确认后单步"。
- **可解释可追溯**：每条提醒追溯来源；每次出网留脱敏摘要；推断区分事实/模型推断/待确认。

## 1.3 权限三层模型

| 层 | 范围 | 控制方式 |
|---|---|---|
| 读取 | 读已授权数据（记忆/账本/快递/日历） | 授权矩阵 + 工具内校验 |
| 执行 | 建提醒、写日历、存备忘、单步点击、深链跳转 | Schema 校验 + 幂等 + 审计；单步前说明目标 |
| 高风险 | 删除/批量修改、对外发送、付款、改系统权限、持续定位/录音/截屏 | 明确二次确认；模型理解意图 ≠ 获得执行权限 |

**【V3.1】确认分档（借 DSH-Go 三档，替换"每步都问"）**

| 档 | 行为 | 适用 |
|---|---|---|
| 允许一次 | 只这一下 | **默认** |
| 本轮允许 | 本次任务内同类操作不再问（任务结束即失效，不跨会话） | 连续同类单步（连填 3 个字段） |
| 取消 | 停止本轮 | — |

**硬约束（不受分档影响，永不放开）**：
1. 支付、银行、券商类界面一律不碰（识别到即停）；
2. 密码、验证码、身份证输入一律交还用户；
3. 不发消息、不代付款、不批量点屏（产品红线，比任何"允许"档位优先）；
4. 系统设置、权限页、App 自身设置页默认拒绝；
5. 3 分钟无操作自动结束本轮；息屏即停；
6. 关闭"屏幕操作"开关，立即中止所有在途操作。

## 1.4 本周期总方针

1. **功能冻结线**：A–E 验收前不新增功能域。**替换实现不算新增功能域**——把 79 行自研周期规则换成本库，不加任何用户可见能力，允许在冻结期内做。
2. **区分已实现/已验收/规划中**：配置预留、死代码、伪实现不得宣称为能力。
3. **隐私优先于功能**：D1–D6 先于一切新功能，也先于整库加密。
4. **提醒宁缺毋滥**：误报一次损害大于漏报一次；置信度三级机制。
5. **复用优先**：见第零部分。
6. **资料为开发服务**：按阶段定向收集，不囤积。

**C 类 系统级调整**（整库加密/大规模迁移/核心重构/换推理运行时/改出网策略/引高敏感权限/**引 native 依赖或 AGPL 代码**）：专项方案 + 风险评估 + 用户明确批准 + 独立 Demo 或副本演练先行；**禁止在唯一真实数据上试错**。

**复用专用判据**：加一个纯 Java、<1MB、有单测覆盖的库 = B 类；加 native so / 引入 AGPL / 超过 3MB = C 类。

## 附录 C 提醒置信度三级机制

```text
高置信：明确日期+时刻+事件完整 → 自动建提醒（现有链路），通知带来源与依据
中置信：时间可解析但语义含糊 / 只有日期或只有时刻 / 群聊转述
        → 写入"待确认"，简报或面板一键确认后才建
低置信：仅疑似时间词、无法确定未来性、噪声源 → 只存不提醒
```
配套：每条存 confidence + 依据；用户纠正回写为样本；待确认超 N 天自动归档；验收 = 误报率逐周下降且高置信准点率不回退。

## 附录 D 记忆管理原则

| 记忆类型 | 例子 | 管理方式 |
|---|---|---|
| 基础事实 | 常用设备、工号 | 长期保存，用户纠正优先 |
| 偏好 | 喜欢的表达方式 | 持续修正，保留修正历史 |
| 习惯 | 通常几点开始工作 | 随新数据更新，标注统计依据 |
| 事件 | 上周参加的会议 | 可检索、有时间范围、来源追溯 |
| 临时状态 | 今天要处理的事 | 过期归档，不自动续期 |
| 推断 | 可能不喜欢某种安排 | 标置信度 + 推断标记；低置信不进长期记忆 |

冲突处理：区分"偏好变化/临时情况/记忆错误"，不擅自覆盖旧记忆，新记录带时间与来源，冲突并存标"待确认"，用户裁决后更新；检索返回来源证据，无依据必须答"没有找到"。

## 附录 E Agent 任务链验收范式

