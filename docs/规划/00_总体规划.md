## 1. 这份规划管什么

**管**：从"现在这个 70 次提交、能装能跑、但没有测试网也没有备份的工程"走到"可交付的个人助理"之间的顺序、门禁和验收。

**不管**：具体 UI 长什么样、模型选哪家、产品功能取舍。这些按需再定，不写进路线图。

**一句话判断**：这不是一个"从零开始的项目"，是一个**跑到一半、跑得还挺快、但没系安全带**的项目。所以第一段不加速，先系安全带。

## 3. 五条基本原则

1. **先证据后结论**。任何"已完成"必须能指到一条命令、一份日志或一张截图。数字不许手写（V3.0 已立此规，本次继续执行）。
2. **一次只动一层**。要么动数据，要么动逻辑，要么动界面。同一提交里混三层，出问题无法定位。
3. **不新建已有之物**。`ReminderEngine`、`ExtractPipeline`、`ActionGate`、`CloudClient` 都已经跑在真机上；新需求优先"扩字段/加接口"，而不是"另起一套"。
4. **可回滚优先于可优化**。每个提交必须能单独 revert；数据库变更必须能降级。
5. **模拟器管重复，真机管真实**。模拟器跑可重复回归；真机跑 5 分钟冒烟 + 硬件专项。两者不互相替代。

## 4. 阶段结构（四段 + 一道硬件关）

```
P-1 稳态化  S0 口径 → S1 密钥 → S2 冷备与双源 → S3 测试地基 → S4 漏收率 → S5 回归脚本
                          ↑ 门禁 G1：一条命令能跑完整回归
P-2 记忆基石 M1  entity / fact / 溯源 / 检索口径
                          ↑ 门禁 G2：一条事实能点回原始收件
P-3 事务闭环 M2 任务四象限 → M3 主动助理（周报 + 3 类发现）
P-4 形态     M4 本地工作台（自检面板升格）+ 本地推理收口
                          ↑ 门禁 G3：真机 24h + 16KB + 温度功耗
P-5 硬件验收 真机专项（不设功能，只出数）
```

### 三道门禁（不过不进下一段）

| 门禁 | 判据（全部满足才算过） | 谁验 |
|---|---|---|

## 9. 变更控制

以下情况才允许改本规划，且必须在 `02_执行记录` 留一条：

1. 门禁判据被证明不可达（例如某测试原理上无法 JVM 化）；
2. 出现比当前阶段更严重的风险（数据丢失、隐私事故、密钥泄漏）；
3. 用户明确改变产品范围或设备目标；
4. 实测数据推翻某条假设（例如漏收率 30%，则 S4 升级为 S5 的前置）。

**不允许**因为"这个功能更想先做"而插队。想插队，先写一条变更记录。
