## 二、逐项分析

### 2.1 地理围栏

#### 2.1.1 用的是哪套 API

**`LocationManager.addProximityAlert`**，不是 GeofencingClient。

- 注册：`GeoFence.kt:151-153`（`proximityPi()` → `lm.addProximityAlert(lat, lng, 300f, -1L, pi)`）
- 半径 300 m：`GeoFence.kt:45`；永不过期 `TIMEOUT_NONE = -1L`：`:54`
- 回调目标：`GeoFenceReceiver`（`GeoFence.kt:362`），Manifest 声明在 `AndroidManifest.xml:66-68`（`exported="false"`，显式 Intent，系统可投递）
- PendingIntent mutability：`GeoFence.kt:230-232` 在 S+ 用 `FLAG_MUTABLE`，**这是对的** —— AOSP 在 API 31+ 对 `addProximityAlert` 会校验 `"pending intent must be mutable"`，用 IMMUTABLE 会直接抛异常（[LocationManager.java 源码](https://cs.android.com/android/platform/superproject/main/+/main:/frameworks/base/location/java/android/location/LocationManager.java)）
- 去重：24h 内同点只响一次（`GeoFence.kt:271-284`）；响完立刻拆（`:385`），靠 `FLAG_NO_CREATE` 找回同一个 PI（`:220-228`）

**选型理由已过期（文档债务，不影响运行）**：`GeoFence.kt:19-22` 写「这台机器没有 GMS，GeofencingClient 一律 ApiException: 13」。但 `CURRENT_STATE.md:31` 已订正为「GMS **完整可用**」，`T-D3` 也未见 GMS 缺失。也就是说这条注释的技术前提已经不成立。
选 `addProximityAlert` 本身仍站得住（零 GMS 依赖、零额外依赖、minSdk 24 全覆盖），但理由要改写成「刻意不绑 GMS」，否则后续维护者会拿错前提做决策。

**废弃状态**：AOSP 源码对该方法标了 `@Deprecated`（建议改用 `LocationRequest` + `Geofence`），但方法在 API 36 仍在、签名未变。`GeoFence.kt:140` 注释写「在 API 34 标记废弃」——官方参考页并未标注具体废弃版本（[developer.android.com · LocationManager](https://developer.android.com/reference/android/location/LocationManager)）。按「已废弃但仍可用」处理，不影响本机运行。

#### 2.1.2 freezer / superkiller 下还能触发吗

分成三层看，结论才准确：

| 层 | 事实 | 判定 |
|---|---|---|
| 注册层 | 围栏对象存在 **system_server 的 LocationManagerService** 里，不在 App 进程里。App 被杀/被冻结，注册本身不消失（除 force-stop / 卸载 / 覆盖安装） | ✅ 不受影响 |
| 评估层 | 进出判定由系统做，需要系统侧有定位流。App **自己没有发过任何 `requestLocationUpdates`**（全仓库无此调用），`saveSpot` 只用 `getLastKnownLocation`（`GeoFence.kt:96-105`）。靠的是 `addProximityAlert` 内部注册的隐式请求 | ⚠️ 依赖系统内部请求不被后台策略掐掉 |
| 执行层 | 判定命中后系统发广播给 `GeoFenceReceiver`，**必须 App 进程真正跑起来执行 `onReceive`** 才能弹通知（`GeoFence.kt:364-386`）。cgroup 冻结态下进程不执行；superkiller 杀掉后要 AMS 重新拉起 | ❌ 这一层是主要风险 |

所以准确的回答是：**「围栏不会因为冻结而丢失，但通知大概率不会按时出现」**。冻结/被杀后，广播要么被 AMS 解冻后投递（迟到），要么被 ROM 直接吞掉。OEM freezer 的典型实现是「只给 FCM / 前台服务解冻，普通广播排队」，星云 OS 属于这一类（`superkiller_enabled=true` + `cgroup_freezer_v2` + `DefendManagerService`，见摸底报告 §4.1 与 §7）。

迟到投递还有一个副作用：`markNotifiedOnce`（`GeoFence.kt:374`）会把「实际收到的时间」当基准，于是用户可能晚上 22:00 才收到「到公司了」——信息已无意义，却仍占掉 24h 配额。代码没有校验「事件时间 vs 当前时间」的陈旧度。

**判定：依赖 ROM 放行（B/C）**。代码层面无法解决，只能靠白名单 + 降级（见第三节）。

#### 2.1.3 「收到围栏广播后自己拉起进程」的路径：没有

`GeoFenceReceiver.onReceive`（`GeoFence.kt:364-386`）逐行看只有四件事：

1. `:366` 取 spot、`:367` 校验是否 home/work
2. `:370-371` 只处理 `KEY_PROXIMITY_ENTERING == true`
3. `:374` 24h 去重 → `:379` `notifyEntered()` 发一条通知
4. `:385` `GeoFence.disarm()` 拆掉两个围栏

**没有** `startActivity`、`startForegroundService`、`WorkManager`/`JobScheduler` 入队、`goAsync()`。也没有 `setFullScreenIntent` 或高优先级通道去争取前台。

所以链路是「广播 → 通知 → 结束」。一旦进程无法执行广播，整条链路就断在系统侧，App 没有任何补救动作。**缺口位置：`GeoFence.kt:379` 与 `:385` 之间**——这里本该有一个「低成本、不弹界面」的兜底动作（例如把待提醒写进库/排一个 `AlarmManager` 一次性闹钟，让系统在下次唤醒时补发），现在什么都没有。

还有一处更根本的断点：**响过一次之后没人重新挂**。

- `GeoFence.kt:27` 注释承诺「下次 arm 由上层在快递入库 / 开 App 时重新挂」
- `GeoFence.kt:138` 再次承诺「下次开 App 挂围栏时通知内容自动是新的」
- 实际：全仓库 `GeoFence.arm(` 只有 **1 处**调用 —— `MainActivity.kt:281`（`onResume`）
- `CourierIntake.kt`、`Express.kt`、`ShareReceiverActivity.kt`、`NotificationsListenerService.kt` 全部无 `GeoFence` 引用（grep 已验证）

结果：围栏是「一次性消耗品」，用完必须等用户再打开 App 才复活。对「到家提醒取快递」这个场景，等于**一辈子只可能提醒一次**。

#### 2.1.4 其余具体缺口（按严重度）

| 级别 | 缺口 | 位置 | 后果 |
|---|---|---|---|
| P1 | 没有 `ACCESS_BACKGROUND_LOCATION`，只有 `ACCESS_FINE_LOCATION` | `AndroidManifest.xml:26` | 后台定位受 Android 10+ 限制；官方 Geofencing 文档明确要求 `ACCESS_BACKGROUND_LOCATION`（target 29+）（[链接](https://developer.android.com/develop/sensors-and-location/location/geofencing)）。proximity alert 是否同样受该 AppOp 约束，官方文档未写明 → 必须真机验 |
| P1 | 重启后不恢复围栏 | `BootReceiver.kt:14-28`（只 `ensureAlarms` / `schedule` / `scanAsync`） | 关机再开机，围栏全丢，要开 App 才回来 |
| P2 | 存完点不 arm | `MainActivity.kt:412-417` | 用户「记住当前位置」后锁屏，围栏实际没挂上，界面上却没有任何提示 |
| P2 | 通知失败仍消耗 24h 配额 | `GeoFence.kt:374` 在 `:379` 之前；`notifyEntered` 内部 `:345-351` 把 `Throwable` 吞成日志 | Android 13+ 没给 `POST_NOTIFICATIONS` 时：什么都没弹，但 24h 内不会再提醒 |
| P2 | 只认 FINE，用户选「大致位置」即视为无权限 | `GeoFence.kt:76-78` | 提示「没有定位权限」，但系统里明明开着定位 → 用户无法自查。注：FINE 在 Manifest 层隐含 COARSE，仅授予 COARSE 时 `hasPermission()` 返回 false |
| P3 | 通道 `IMPORTANCE_DEFAULT` + 静音 + 无震动 | `GeoFence.kt:294-300` | 星云 OS 可能把静默通道折叠，通知实际不可见 |

### 2.2 无障碍

#### 2.2.1 声明了哪些 capability

全部在 `res/xml/a11y_service.xml:12-18`：

| 属性 | 值 | 含义 |
|---|---|---|
| `accessibilityEventTypes` | `typeWindowStateChanged` | 只在切窗口时回调（省电设计） |
| `accessibilityFeedbackType` | `feedbackGeneric` | 不做语音反馈 |
| `accessibilityFlags` | `flagDefault` | **不含** `flagRetrieveInteractiveWindows`、`flagReportViewIds`、`flagIncludeNotImportantViews` |
| `canRetrieveWindowContent` | `true` | 可读节点树 ✅ |
| `description` | `@string/a11y_desc` | 已定义（`res/values/strings.xml:14`） |
| `notificationTimeout` | `100` | 事件合并窗口 |
| **`canPerformGestures`** | **未声明（=false）** | **不能 dispatchGesture** |
| `canRequestFilterKeyEvents` | 未声明 | 不能拦按键 |

服务本体：`ZhuliA11yService.kt:30-77`。`onAccessibilityEvent` 空实现（`:58-60`，刻意的），节点树由 `UiBridge` 按需抓一次（`UiBridge.kt:57`）。

Manifest 声明：`AndroidManifest.xml:54-64`，`permission="android.permission.BIND_ACCESSIBILITY_SERVICE"`（签名级，只有系统能绑），`exported="true"` 是该组件类型的要求，不构成额外暴露。

#### 2.2.2 能不能点击 / 滑动

**点击：能，而且实现是对的。**

- 节点点击：`UiBridge.kt:166-173`，`c.performAction(AccessibilityNodeInfo.ACTION_CLICK)`
- 可点祖先上溯最多 3 层：`UiBridge.kt:175` + `:159-186`（真实布局里 TextView 常不可点，靠这层兜住）
- 全局返回 / Home：`UiBridge.kt:130-133` → `:137-145` `performGlobalAction`
- 命中后**只点一次**、不循环、不串联（`:109-110` 命中即 return）
- 用户确认在前：`MainActivity.kt:788-808` 先列出屏幕上可点项，二次确认「要点这个？」，点完只报一行结果

**滑动：代码里没有这条路径。**

- 全仓库 grep `dispatchGesture` / `canPerformGestures` / `GestureDescription`：**0 匹配**
- `a11y_service.xml` 没有 `canPerformGestures="true"`，按官方文档，没有该声明调用 `dispatchGesture()` 直接不可用（[Create an accessibility service](https://developer.android.com/guide/topics/ui/accessibility/service)）

**这条要回写进摸底报告**：设备报告 §9 第 15 项写的「无障碍点击/滑动」在代码里只有「点击」，没有「滑动」。当前产品能力应表述为「**读屏 + 单步点击**」，不是「点击/滑动」。

另外两个能力缺口，影响读屏准确度：

- 没有 `flagRetrieveInteractiveWindows` → 只能用 `rootInActiveWindow`（`UiBridge.kt:57`），**弹窗/悬浮窗/分屏的第二个窗口读不到**，`rootInActiveWindow` 也可能返回 null
- 没有 `flagReportViewIds` → `viewIdResourceName` 恒为 null（代码没用到，暂无影响，但后续想按 id 定位就得加）

#### 2.2.3 节点失效 / 超时的兜底

**有兜底，但只兜「不崩」，不兜「点错」。**

已有的：

| 兜底 | 位置 |
|---|---|
| 单节点读取失败不中断遍历 | `UiBridge.kt:74-79`（`catch` 后继续跑队列） |
| 全流程异常兜底 | `UiBridge.kt:81-84`（返回 `emptyList`）、`:123-126`（返回 `false`） |
| `performAction` 失败兜底 | `UiBridge.kt:167-172`（catch → false → 继续向上找祖先） |
| 节点泄漏防护 | `UiBridge.kt:202-208` `recycleQuietly`（API 24 必回收，33+ 空实现） |
| 服务死亡清单例 | `ZhuliA11yService.kt:43-47`（`onUnbind`）、`:49-52`（`onDestroy`） |
| 遍历上限 | `UiBridge.kt:35` `MAX_NODES = 300`，防大页面卡主线程 |

没有的（都是真实缺口）：

| 缺口 | 后果 | 级别 |
|---|---|---|
| 无 `node.refresh()` | 界面已变、节点句柄还是旧的 → 读到过期文字或点空 | P2 |
| 无 `isVisibleToUser` 校验 | 半滚出屏幕的 item 也会进候选列表（`:61-79` 没过滤），用户选了会点到不可见控件 | P2 |
| 无重试 | `performAction` 返回 false 直接放弃（`:173`），不重抓一次节点树再试 | P3 |
| 无超时 | `performAction` 是同步 binder 调用，系统卡住时主线程跟着等（binder 默认超时量级 5s）。调用点都在主线程（`MainActivity.kt:799`），最坏表现为**界面卡一下** | P3 |
| 无失败原因上报 | 失败只进 logcat（`Log.w(TAG, ...)`），用户只看到「这个元素点不了」 | P2（可诊断性） |

`MAX_TEXT_LEN = 40` + 纯符号过滤（`UiBridge.kt:188-195`）会把长按钮文案和「·」「—」剔掉，属于合理取舍。

#### 2.2.4 星云 OS 禁用第三方无障碍时，代码怎么表现

**静默失效，不崩溃。** 分三种情形：

| 情形 | 代码路径 | 用户可见表现 |
|---|---|---|
| 用户在设置里关掉开关 | 系统解绑 → `onUnbind`（`ZhuliA11yService.kt:43-47`）→ `instance = null` | 设置页那行回到「屏幕操作（无障碍）▸ 去系统设置开启」（`MainActivity.kt:692-697`），点它跳系统无障碍页（`:698-701`）。功能入口在，只是不可用 |
| 进程被 freezr/superkiller 干掉 | 单例随进程消失 → `instance == null` | 同上，下次开 App 自动恢复判断 |
| **ROM 拦截但开关显示「已开启」**（最坏） | `instance` 非空，`rootInActiveWindow` 返回 null 或 `performAction` 返回 false | `isReady()` 仍为 true（`UiBridge.kt:44`）→ 界面显示「已开启」→ 用户点进去 → 「没读到当前屏幕的文字」（`MainActivity.kt:789-790`）或「这个元素点不了」（`:800`）。**没有任何提示指向「被系统限制」** |

也就是说：第三种情形下 App **自己也不知道坏了**。这是这套设计最大的可诊断性缺口——`UiBridge.isReady()` 只判断「单例非空」，不等于「真的能取到节点」。建议加一个「最近 30 秒内 `rootInActiveWindow` 成功过」的健康位（需新增，本次不改代码）。

**真机已有证据（沿用 T-D3 #5）**：用 `settings put secure enabled_accessibility_services` 写入后，`dumpsys accessibility` 显示 `Service[label=zhuli助理, eventTypes=TYPE_WINDOW_STATE_CHANGED]` 已绑定 → **星云 OS 没有拦绑定**。但注意：这条证据是 adb 直接写设置，**绕过了设置页 UI**，因此「用户手动点开关是否会被 Android 13+ 的受限设置（Restricted settings）挡住」仍未验证。该机制的官方原文我没在 developer.android.com 检索到（第三方资料很多），**按未查到处理**，只列为真机验证项。

**判定汇总**

- 声明与绑定：**依赖 ROM 放行**（已有一半证据：绑定通过；手动开启未验）
- 读 + 单点：**代码完备**
- 滑动：**代码里没有这条路径**（功能未实现，不是被拦）
- 失效表现：**代码完备（静默失效是刻意设计）**，但缺「可诊断」这一层

## 三、降级方案

前提：不改方向、不引入保活库、不做批量自动化。下面每条都对应到现有类，标「已具备」的可直接引用，标「需新增」的给出落点。

### 3.1 围栏不触发时

| 替代路径 | 现有实现 | 状态 | 代价 |
|---|---|---|---|
| A. **到站即提醒**（把「到家」降级成「快递到站」） | `NotificationsListenerService.kt:65-76` → `CourierIntake.intake()` → `ReminderEngine` 建提醒 | **已具备** | 提醒时机提前，但完全不依赖定位与后台唤醒，是最稳的一条 |
| B. **固定时刻闹钟**「18:30 到家取快递」 | `ReminderEngine` + `AlarmManager`（`BootReceiver.kt:22` 已保证重启后重排） | **已具备**（需用户手动设一次时间） | 时间写死，早回家/加班都不准 |
| C. **桌面小组件常驻待取** | `BriefWidget.kt` + `widget_info`（`AndroidManifest.xml:71-80`） | **已具备**（需确认 widget 是否含快递行；`DailyBrief` 里已有快递汇总） | 要点一下桌面才看到 |
| D. **显式组件唤起快递面板** | `MainActivity.kt:224-226` / `:297-299`（`com.zhuli.action.COURIER` → `openCourierPanel()`，`:995`） | **已具备**（adb / 桌面快捷方式 / 自己 App 内可用） | 第三方 App 无法按 action 唤起（见下条） |
| E. 让外部能唤起（Tasker / 快捷指令 / 车机） | `AndroidManifest.xml:40-51` 目前只有 `MAIN`/`LAUNCHER` | **需新增**：给 MainActivity 加 `com.zhuli.action.COURIER` 等 `intent-filter` | 一行 manifest；仍受后台启动限制，只能「用户主动点」 |
| F. 围栏命中后补发 | 无 | **需新增**（落点 `GeoFence.kt:379-385` 之间）：写库 + `AlarmManager` 一次性闹钟，不弹 Activity | 改动小，能把「冻结导致丢失」变成「下次唤醒补发」 |

**推荐组合：A（主）+ C（可见性）+ F（补发）**。A 是唯一不依赖任何后台特权的路径；F 只补「已经触发但没弹出来」这一小段。

### 3.2 无障碍不可用（或被拦）时

| 替代路径 | 现有实现 | 状态 | 说明 |
|---|---|---|---|
| A. **通知操作按钮** | `ReminderNotifier.kt:92-93`（「完成」/「稍后10分钟」）+ `:73-74` / `:260` 的 action PendingIntent | **已具备** | 用户不用点进 App，直接在下拉通知里处置；这条最接近「无障碍点一下」的体验，且完全不需要特殊权限 |
| B. **分享入口** | `ShareReceiverActivity.kt:22,26`（`ACTION_SEND`，text/image/audio/video 四类，`AndroidManifest.xml:92-113`） | **已具备** | 用户在任意 App 里「分享 → zhuli助理」，把「读屏」变成「用户主动送过来」 |
| C. **选中文字处理**（`ACTION_PROCESS_TEXT`） | 无 | **需新增**（落点同上 manifest `<activity>` 内加一个 `<intent-filter>`） | 对「读一段屏幕文字」的替代度最高：用户在任意 App 长按选中 → 菜单里出现「用助理处理」。比无障碍稳，且合规 |
| D. **快捷指令 / 桌面长按** | `res/xml/shortcuts`（`AndroidManifest.xml:48-50`）+ `MainActivity.kt:224-226` | **已具备** | 「记一笔 / 看快递 / 今日简报」三条已通 |

| F. MediaProjection 截屏 + OCR 替代读屏 | 无 | **不推荐** | 需要 FGS + 常驻通知 + 每次授权，隐私成本远高于收益；且 `T-D3 #8/#9` 已确认代码里没有任何 MediaProjection / FGS |

**推荐组合：B + C（覆盖「读」）+ A（覆盖「做」）**。C 是当前最值得补的一块——它把「无障碍读屏」这个高风控能力，换成系统级、用户显式触发的标准入口。

### 3.3 不建议的替代

- 不引第三方保活/唤醒库对抗 freezer（违反项目底线，且 `StartupGuard.kt:31-33` 已明文写死不装）
- 不做「无障碍自动化点完整流程」（`UiBridge.kt:12-18` 的红线，且会被判灰产）
- 不申请 `QUERY_ALL_PACKAGES` 之类特权去绕（与本任务无关，但容易在「想拉起别人」时被顺手加上）

## 五、可直接进 CURRENT_STATE 的短句

- **地理围栏**：实现为 `addProximityAlert`（`GeoFence.kt:151-153`），注册不随进程死亡丢失，但**触发后的通知依赖进程能跑** → 星云 OS freezer 下判「依赖 ROM 放行」（B/C）。代码有 4 处链路断点：只在 `onResume` arm（`MainActivity.kt:281`）、重启不恢复（`BootReceiver.kt:14-28`）、存点后不 arm（`MainActivity.kt:412-417`）、通知失败仍耗 24h 配额（`GeoFence.kt:374`）。「广播后自己拉起」的路径**不存在**。
- **无障碍**：capability 只有「读窗口内容 + `typeWindowStateChanged`」（`a11y_service.xml:12-18`），**无 `canPerformGestures`**，因此只有 `performAction(ACTION_CLICK)` 与全局返回/Home（`UiBridge.kt:166-173`、`:130-133`），**滑动功能未实现**。节点失效有 try/catch 兜底但无 refresh/可见性校验/超时。被 ROM 禁用时**静默失效不崩溃**，且 `isReady()` 仍可能为 true（`UiBridge.kt:44`），缺可诊断性。T-D3 已证绑定不被拦（`settings put` 路径），**用户手动开启是否受 Restricted settings 影响未验**。
