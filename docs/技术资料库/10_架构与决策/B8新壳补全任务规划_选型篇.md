# B8 新壳补全任务规划（选型篇，2026-11-21 22:55，只规划未执行）

> 总原则：**上游已有机制 > 已迁移 core 代码 > 开源库 > 自己写**。
> 本轮调研先查证 LastChat 上游（rikkahub）已内置能力，再搜开源实现佐证，避免重复造轮子。

## 关键调研发现：上游已内置 5 项"以为缺"的能力

| 上游机制 | 位置 | 可直接解决 |
|---|---|---|
| **Assistant 预设**（name + systemPrompt + 默认模型/工具） | `data/model/Assistant.kt:38-52` | M8 人格设置——不写 UI，建预设即可 |
| **定时消息**（ScheduledMessageWorker/Receiver） | `service/ScheduledMessage*` | C3 晨间简报——定时发"生成简报"消息走 Tool 链 |

| **加密备份**（BackupArchiveFormat + SecureStore/SecretKeyManager） | `data/sync/`、`data/datastore/` | A1 备份——扩展一个 zhuli_inbox.db 条目 |
| **Sherpa ASR 全套**（ASRController/DownloadManager/Service） | `speech/asr/` | SHOULD 语音——接聊天页入口 |

另有：**多模态图片输入**（GenerationHandler image parts）已内置——图片理解可直接走云模型。

## 逐项选型

### P0 立即（量小、复用度高）

**P0-1 OEM 保活（B4 硬验收，零代码）**
- 选型：无代码，用户手动设置。开源佐证：dontkillmyapp.com + 努比亚四步法（mytju.com 转帖实测）。
- 步骤：①手机管家→权限管理→LastChat→允许后台启动 ②通知重要程度设"高/紧急" ③多任务界面下拉锁定 ④电量管理→应用省电→不管控。兜底：`adb shell dumpsys deviceidle whitelist +lastchat.rikkafork.cocolal.dev`。
- 注意：旧壳卸载后白名单按包名失效，必须对新包名重做。

**P0-2 人格接线（M8）**
- 选型：**复用上游 Assistant 预设**。把已迁移的 `core/Persona.kt` 数据转换导入一个 Assistant 预设（name="zhuli"，systemPrompt=人设+语气+开场白），设为默认 assistant。
- 工作量：小（数据转换 + 导入逻辑），零新 UI。
- 佐证：rikkahub 的 assistant 机制本身就是"纯数据驱动人格"（与需求文档 §2.5 定稿原则完全一致）。

**P0-3 晨间简报接线（C3）**
- 选型：**复用上游 ScheduledMessageWorker**。每天 7:30 定时发一条"给我今日简报"到默认会话，模型走 list_todo/ledger/search_memory Tool 生成简报（周末加周报文案分支）。
- 工作量：小（定时任务配置 + 简报 prompt）。
- 前置依赖：P0-2（人格预设让简报语气统一）。

### P1 短期（标准机制，小改动）

**P1-1 分享目标（M2 输入层另一半）**
- 选型：标准 Android 机制（Manifest `ACTION_SEND`/`ACTION_PROCESS_TEXT` intent-filter + 路由到对话输入框预填），**无需开源库**。上游 ShareSheet 是导出方向，接收需自加（标准写法，参考任意开源分享接收实现）。
- 工作量：小-中（intent-filter + 一个路由 Activity/入口判断）。

**P1-2 备份扩展（A1）**
- 选型：**复用上游 BackupArchiveFormat/SecureStore**——在备份清单里加 `zhuli_inbox.db` 条目（含恢复侧）。
- 工作量：小。
- 佐证：LastChat 备份目前只含 rikka_hub.db + workspace files（已查证 BackupArchiveFormat.kt:28）。

**P1-3 误操作撤回补全（B2）**
- 选型：ReminderActionReceiver 已迁（完成/稍后按钮在）——补一个"撤销"action（数秒内撤，删除提醒+取消闹钟）。
- 工作量：小。

### P2 中期（引入开源库，有明确佐证）

**P2-1 数据库加密（A2）**
- 选型：**SQLCipher**（`net.zetetic:sqlcipher-android:4.9.0`，开源标准方案）+ Android Keystore 管理 key（随机 256-bit，运行时生成，GCM 加密存于 prefs）+ `ATTACH DATABASE / sqlcipher_export` 迁移现有明文库。
- 佐证：多来源一致（Mycelium Sys 2025 / CSDN 终极指南 / 安策企业实践）——key 不落盘、关闭时清内存、5-15% 性能开销、迁移路径成熟。
- 注意：zhuli 库是原生 SQLiteDatabase（非 Room），用 sqlcipher 的原生 API 版；LastChat 自身 rikka_hub.db 是否同加密另行决策。
- 工作量：中（依赖接入 + openHelper 替换 + 迁移脚本 + App 锁 PIN/生物识别——App 锁可复用上游或 androidx.biometric）。

**P2-2 支付截图入账 OCR**
- 选型：**ML Kit text-recognition-chinese**（bundled 离线、免费、中文强、25MB 模型、~30ms）；备选 PaddleOCR（精度更高但 JNI 复杂、+12.7MB）。
- 场景分工：结构化文字提取走 ML Kit；语义理解（截图上下文判断）走多模态云模型（上游图片输入已内置）。
- 佐证：ML Kit 实战文章（2026）+ 百度智能云对比文——ML Kit 中文 OCR 是国内轻量首选。
- 工作量：中（依赖 + 截图入口 + 识别→Ledger 流水线对接）。

### P3 长期（迁已建代码 / 按需）

**P3-1 地理提醒**：迁旧壳 GeoFence 代码（已建、真机验过触发），精确定位权限已授。中等工作量。
**P3-2 语音输入入口**：上游 Sherpa ASR 全套在，聊天页接入语音按钮 + 旧壳"语音消息转写入库"流水线对接。中等工作量。
**P3-3 媒体存储策略（D3）**：随 P2-2 OCR/图片功能一起做（缩略图+摘要策略）。
**P3-4 数据导出（D4）**：BackupJson 已迁，加导出入口（JSON/CSV）复用 LastChat 分享机制。小。

### ❌ 明确不做（WON'T）

**剪贴板后台监听（A4/B2 里的剪贴板部分）**：Android 10+ 系统级禁止后台读剪贴板（root 也不行）。开源界的实现全是重方案：Shizuku 客户端（ClipStack v2.5.0）、自定义输入法 IME、无障碍猜测式监听（XClipper）——均超出助理 App 合理复杂度，且 A4 的"雷区过滤"本意就是丢弃敏感剪贴板。**降级决策：不做后台监听；前台粘贴（LastChat 输入框已支持）+ 分享目标（P1-1）覆盖真实场景。**

## 附录：Shizuku 路线（2026-11-21 23:05，用户确认设备已装 Shizuku 并愿授权）

用户有 Shizuku → **剪贴板监听从 WON'T 升级为可做**，且 Shizuku 可顺带自动化多项授权。Shizuku 与 rikkahub 同属 rikka.dev 生态，依赖接入天然顺。

### S1 剪贴板后台监听（A4/B2 剪贴板部分，原 WON'T → 现可做）
- **开源参考（已搜证）**：ClipStack v2.5.0（github.com/liliangxing/ClipStack，Shizuku 集成版）——
  - 机制：主 App 作为 Shizuku client；在 **Shizuku server 进程**内跑一个 shell（UID 2000）用户服务，shell 用户豁免 Android 10+ 后台剪贴板限制；
  - 实现：AIDL（IClipboardService/IClipboardCallback）跨进程回传；ShizukuClipboardService 在 server 进程注册 `ClipboardManager.OnPrimaryClipChangedListener`；ShizukuManager 单例管连接生命周期；**优雅降级**：无 Shizuku → 前台 legacy 监听（Android 9- 及前台焦点场景）。
  - 依赖：`dev.rikka.shizuku:api` + `dev.rikka.shizuku:provider`（rikka maven repo，LastChat 构建环境已兼容 rikka 生态）。
- **zhuli 接入设计**：监听回调 → **A4 雷区过滤先行**（密码/卡号/验证码/token 命中即丢弃，不入库）→ 通过 NoiseGuard → InboxDatabase.insert → ExtractPipeline.trigger（复用现有管道）。
- **隐私口径**：剪贴板内容按 D2 默认视为敏感倾向；过滤后仍入库的走本地（不自动出网）。
- 工作量：中（AIDL + 用户服务 + IPC + 过滤对接）。

### S2 Shizuku 授权向导（P0-1 保活的自动化增强）
- 用户有 Shizuku → 下列 adb 等效命令可由 shell uid 执行，做成"授权向导"页一键完成：
  - `dumpsys deviceidle whitelist +lastchat.rikkafork.cocolal.dev`（电池优化豁免）
  - `pm grant … READ_CALENDAR / WRITE_CALENDAR / READ_SMS`（C4 日历写回与短信源的一次性授权）
  - `appops set … SCHEDULE_EXACT_ALARM allow`（精确闹钟特殊权限）
  - `cmd notification allow_listener …/AssistantNotificationListener`（通知使用权，重装后一键恢复）
- 努比亚手机管家的"允许后台启动"是私有设置，Shizuku shell 不保证可达——**此一步仍手动**（四步法其余三步可自动化）。
- 工作量：小-中（Shizuku 命令执行器 + 向导 UI；可并入现有自检面板 tab）。

## DSH-Go 调研结论（2026-11-22 00:40，用户点名调研）

**dsh-Go**（github.com/ccch1mneyyy/dsh-Go，23k stars，AGPL-3.0）：Android 端跑 DeepSeek Harness（PRoot Ubuntu+Node.js 容器，196MB APK，无 root）。
- **手机控制三层确认**：默认每次问 / 本轮跳过 / 总是跳过（需二次确认）；确认卡 30 秒自动拒绝；支付/银行/券商默认黑名单；微信逐步确认；3 分钟无操作自动结束；息屏停任务——**与 zhuli ActionGate 三档确认几乎逐条一致**（T-B11 设计时即"借 DSH-Go"，相互印证为业界最佳实践）。
- **可中断生成**（发送即插队/插入当前轮）——值得借鉴（体验增强项，LastChat 排队机制现状待查）。
- **联网搜索/图像理解**：zhuli 无需引入——LastChat 上游已内置（Assistant.searchMode 内置搜索 + 多模态图片输入）。
- **不适用项**：PRoot Linux 容器（zhuli 是生活助理非代码 agent）；手机操作（违反 zhuli A3"只收不发"边界）。
- **ROM 保活识别跳转**（识别厂商跳设置页）——zhuli Shizuku 向导已覆盖大半，可加"跳转厂商设置"按钮（小改）。
- OpenCode 为桌面 coding agent，机制同 dsh-Go 类，对 zhuli 参考价值同上。
