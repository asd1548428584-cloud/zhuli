# ADR-0002 备份密钥体系：现有 Keystore 方案不可迁移，需引入口令派生

- **编号**：0002
- **日期**：2026-11-20
- **状态**：**提议**（待用户拍板 §11-6，实施属阶段 E 的 T-E2【C 类】）

## 问题背景

缺陷 D7：现有加密备份（`Backup.kt`）用 Android Keystore 密钥加密，落到 `files/backups/*.json.enc`。
Keystore 密钥随应用卸载销毁、且与本设备绑定（见 `08_安全与隐私/资料卡片_AndroidKeystore.md`）。
后果：**卸载、换机、双清之后，备份文件在也解不开**——备份等于没有。

交接文档里"换机时把 backups 拷回去就能恢复"的说法是错的，已在文档修订注记中纠正。
当前唯一可用的逃生通道是 T-A1 的明文拉库 + `run-as` 回灌，它依赖"包必须可调试"。

## 候选方案

| 方案 | 加密密钥 | 可迁移 | 用户体验 | 风险 |
|---|---|---|---|---|
| A 维持 Keystore（现状） | 设备内不可导出密钥 | **否** | 无感 | 换机即丢数据；D7 不关闭 |
| B 口令派生（PBKDF2/Argon2 + 随机盐） | 用户口令派生 | **是** | 备份/恢复各输一次口令 | 口令丢失 = 永久不可恢复；口令强度决定安全性 |
| C 混合：Keystore 本地 + 口令导出包 | 两套 | 是（导出包） | 日常自动、迁移时额外一步 | 实现与测试成本最高 |

## 比较依据

- A 已被实证否定（2026-11-20 卸载重装，密文不可解）；
- C 的"日常无感"很吸引人，但它要求两套密钥体系长期共存，且导出包的密钥管理仍是 B 的问题，等于把 B 做一遍再加一层；
- B 是唯一能真正解决"跨设备恢复"的最小方案，代价是把"密钥保管责任"明确交给用户。

## 提议

**选 B**，并按计划 §6.E T-E2 执行：
1. 备份格式升到 v11 全表（现在 version=9，缺 skills/embeddings/cloud_log）；
2. 口令派生密钥（PBKDF2-SHA256，迭代 ≥ 20 万，16 字节随机盐，AES-GCM）；
3. 保留 Keystore 加密的"本地快速备份"作为辅助，但**文档不得再宣称它可跨设备**；
4. 恢复流程做两次安装/两台设备演练后才算通过。

## 影响模块

`Backup.kt`（格式与密钥）、`AppLock.kt`（PIN 与备份口令是否统一，需定）、恢复入口 UI、`换机交接.md`（再次纠正）。

## 风险

- 口令丢失 = 数据永久不可恢复，必须在界面上明示并要求二次确认；
- 迭代次数过高会让低端机备份变慢，20 万次是本项目的初始取值，需实测；
- 若用户把口令和备份文件放一起，等于没加密。

## 验证方式

- 本机备份 → 卸载 → 重装 → 用口令恢复 → 行数与 `user_version` 对齐；
- 错误口令 → 明确报错且不破坏已有库；
- 换一台设备（或用模拟器）重复一次。

## 回滚方案

保留旧格式读取能力（能读 v9），但不再写 v9。若 B 方案实施失败，仍可用 T-A1 明文拉库兜底。

## 待用户确认

§11-6：是否采纳口令派生方案；PIN 与备份口令是否合并为一个（合并更省事，但 PIN 通常是 4–6 位数字，强度不足以派生密钥，**不提议合并**）。
