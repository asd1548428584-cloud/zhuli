## 一、一页看全貌

**做的是什么**：把手机上散在通知、短信、分享菜单里的信息收进本地库 → 抽出时间/金额/取件码 → 到点提醒 → 并且能用一句话问出来。数据默认不出机。

**代码形态**：LastChat（开源安卓聊天客户端）的 fork。全仓 794 个 `.kt` / 19.4 万行，其中**自研 `com.zhuli` 包 76 个文件 / 约 1.1 万行**（含测试），剩下是上游。所以"工程量"要看后者。

**进度总览**

| 阶段 | 内容 | 状态 | 完成度自评 |
|---|---|---|---|
| A | 工程基线（构建/签名/备份/可复现编译） | ✅ | 100% |
| B | 隐私与出网闸门 | ✅ | 100%（曾整体推翻重验一次） |
| C | 检索与提醒可靠性 | ✅ | 95%（FTS 方案实测后主动放弃） |
| D | 提醒可靠性十项场景 | 🟡 | 80%（2 项真机未验） |
| E | 数据安全（锁/备份/导出） | 🟡 | 60%（缺整库加密） |

## 二、功能清单：实现了什么 + 靠什么实现

### A. 采集：东西是怎么进来的

| 功能 | 状态 | 实现方式 | 局限 / 证据 |
|---|---|---|---|
| 通知监听入库 | ✅ | `AssistantNotificationListener : NotificationListenerService`（Manifest 注册 `BIND_NOTIFICATION_LISTENER_SERVICE`），回调里取 `title/text/bigText`，先过 `NoiseGuard` 再写 `inbox` | 真机 436 条验证；该权限需用户手开，重装后靠 Shizuku 一键恢复 |
| 噪声过滤 | ✅ | `NoiseGuard.dropReason()` 四道护栏：①来源已静音 ②回声源（日历/时钟，避免自己收自己）③低信号源（计步/商店）④同文去重 10 分钟/标题累加/频率 20 条 | 修过 B 站 7 条同刻同标题的批量误报（误报率 85.7% → 1 条真实项） |
| 按来源静音 | ✅ | `source_rule` 表 + 自检面板入口，按包名静音/恢复 | 真机验证；B 站+iKuuu 曾占 78% 流量，静音后压掉 |
| 分享菜单收文字/图 | ✅ | 上游 SEND intent → 路由到 `ExtractPipeline`，图片走 ML Kit 中文 OCR | 真机验证 |
| 短信取件码 | ✅ | `ZhuliSmsReceiver`（只听 `SMS_RECEIVED`）→ 只喂 `CourierIntake`，非快递短信读完即丢；另有 READ_SMS 扫近 7 天 | 曾因迁移整体丢失，已补回（Manifest + Receiver + 自检卡 + 向导项，4 例测试） |
| 链接正文抓取 | ✅ | `LinkExtractor` 纯 Kotlin HTML 解析，只取标题+正文首段 | 单测覆盖；不跑 JS，公众号等动态页抓不全 |
| 视频理解 | 🟡 | 抽帧 + OCR，音轨转写没接 | **从未复验**，缺真实素材 |
| 剪贴板 | ⬜ | 规划走 Shizuku shell 用户服务读剪贴板 → 隐私过滤 → 入库 | P1.5，未动工 |

### B. 理解：怎么变成结构化数据

| 功能 | 状态 | 实现方式 | 局限 / 证据 |
|---|---|---|---|
| 分类 | ✅ | `ExtractPipeline.classify()`：正则命中决定 快递/金融/工作/生活/链接/其他 六类；"有时间又没提钱"="生活" | 纯规则，无模型；换个说法就归"其他" |
| 时间解析 | ✅ | `TimeParser` + `parseDeadline()`，覆盖"下周三""明天下午三点""15 号""3 小时后"、中文数字、时段默认值（上午/下午） | 6 例单测；认不出返回 0，不瞎猜 |
| 周期规则 | ✅ | `parseRepeat()` → **RFC5545 字符串**（`BYDAY=MO` / `BYMONTHDAY=-1`）存库，`Repeat` 负责算下次 | 12 例单测；v14 迁移把旧的 `weekly:2` 迁成 RFC5545 |
| 金额抽取与记账 | ✅ | `parseAmount()` 正则 + 过滤，写 `ledger` 表（收/支/分类/来源） | 只看文本里的数字，账单截图要靠 OCR |
| 快递识别 | ✅ | `CourierIntake` + `Express`：承运商词典 + 驿站名 + 取件码正则；置信度由 `ReminderConfidence` 判（有码=高置信） | 真机：韵达/圆通/极兔三种短信 10/10 通道完整 |
| 敏感信息闸门 | ✅ | `SensitiveGuard` 识别证件号/卡号/验证码 → 分"可脱敏"与"红线不发"两档 | 红线类（验证码）脱敏也不发 |
| 待补抽取 | ✅ | `pending_extract` 列：规则没抽出来的记录挂起，等模型/后续补 | 避免一次性丢数据 |

### C. 存储：数据放哪

SQLite 单库 `zhuli_inbox.db`，**v14**，8 张表：

| 表 | 内容 | 关键设计 |
|---|---|---|
| `inbox` | 收件（通知/短信/分享/链接/OCR） | 索引打在 `received / pending_extract / category / deadline` 上 |
| `reminders` | 提醒 | 存 RFC5545 周期、`snooze_count`、`calendar_event_id`、原时刻（供撤销） |
| `ledger` | 账本 | 收/支 + 分类 + 来源 id |
| `chat_log` | 对话记录 | 冷启动回上次会话靠它 |
| `embeddings` | 向量（256 维） | 只有向量列 + 时间窗查询 |
| `source_rule` | 按来源静音规则 | 包名 → 静音/恢复 |
| `cloud_log` | 出网留档 | 每次上云一条脱敏摘要，App 内可查 |
| `skills` | 技能表 | 预留，当前 0 行 |

检索策略（有实测依据）：**LIKE 为主力**，混一路 256 维向量做语义补充。向量当前是 **hash embedder 占位实现**（`HashEmbedder`，字符 3-gram 哈希到 256 维），不是真模型；代码留了 `GemmaProvider` 的替换口。

> 实测反证：中文 trigram 全文检索被**主动否掉**——40 个真实高频词只召回 17/40，因为两字词占 23 个而 trigram 要求 ≥3 字。这是这个项目里少数"做完实验再放弃"的决策。

### D. 输出：提醒怎么保证响

| 功能 | 状态 | 实现方式 | 局限 / 证据 |
|---|---|---|---|
| 准点提醒 | ✅ | `ReminderEngine` 用 `AlarmManager`：优先 `setAlarmClock()`（最高优先级），无权限则 `setExactAndAllowWhileIdle` → `setAndAllowWhileIdle` **三级降级，绝不因缺权限崩溃**；进程被杀也能响 | 真机偏差 0 秒；关屏/Doze 下有验证 |
| 通知动作 | ✅ | `ZhuliReminderActionReceiver` 三个 action：完成 / 稍后 10 分钟 / 撤销（撤销=按 prefs journal 恢复原时刻重挂闹钟） | 真机 75 秒实测三动作齐全 |
| 周期顺延 | ✅ | `Repeat` 按 RFC5545 算下一次，触发后自动重挂 | 模拟器通过，真机走动未验 |
| 迟到补响 | ✅ | 晚到 2 分钟内补响而非静默取消 | 修过 D15 静默取消缺陷 |
| 写系统日历 | ✅ | `CalendarWriter` 写 CalendarContract，回存 `calendar_event_id` | 曾因迁移漏 `WRITE_CALENDAR` 声明而静默失效，已补 |
| 每日简报 | ✅ | `ZhuliDailyBrief`：数字全部本地算（件数/待办/花费），模型只负责"写一段人话"；`ZhuliBriefWorker` 每天 07:30 落库可回看，首启弹一次 | 真机：杀进程重开会话与消息都在 |
| 桌面小组件 | 🟡 | 有实现 | 渲染未验 |
| 崩溃落盘 | ✅ | `ZhuliLog` 写文件 + 崩溃页 + 分享入口 | 真机触发钩子验过；该 ROM `logcat` 为空，只能靠这个 |

### E. 对话：问得出来

两套并行，谁合适用谁——这是整个设计里最关键的一点：

| 路径 | 状态 | 实现方式 |
|---|---|---|
| **规则直答（不联网）** | ✅ | `ZhuliIntentRouter`：关键词命中 快递/账本/待办 三类意图 → `ZhuliQueryTools` 查库 → 模板拼答案。常见问句**完全不经过模型**，毫秒级、可预期 |
| **两跳确认** | ✅ | 意图命中但缺参数（如"我快递到哪了"要先确认是查待取还是查已签收）→ 反问一句 → 用户回"确认" → `ZhuliActionConfirm` 放行 |
| **模型 + 工具** | ✅ | `CloudClient`（OpenAI 兼容）带 **6 个工具**：`search_memory` / `list_todo` / `ledger_summary` / `list_courier` / `save_memory` / `create_reminder`。模型只能通过工具看数据，工具返回什么它说什么 |
| **端侧小模型** | ✅ | Qwen3-0.6B（613MB，LiteRT）装机可切；**只做标题/摘要，不做标题生成**（曾因小模型跑飞导致标题乱码） |
| **隐私闸门** | ✅ | `PrivacyRouter.decide()` 三档：直接发 / 脱敏后发 / 红线不发；每次上云 `cloud_log` 留一条脱敏记录 |
| **动作闸门** | ✅ | `ActionGate` + `ActionConfirm`：任何写操作（建提醒、写日历）必须用户确认，模型无权自决 |

### F. 权限与自检：怎么让你知道它还活着

| 功能 | 状态 | 实现方式 |
|---|---|---|
| Shizuku 一键授权 | ✅ | `ZhuliShizukuRunner` 用 Shizuku 以 shell 身份执行 5 条命令：电池豁免 / 日历 / 短信 / 精确闹钟 / 通知使用权。每条回传 `[exit=N]`，**非 0 判失败** |
| 自检面板 | ✅ | `ZhuliSelfCheck` 14 行 / 6 组：①采集 ②知道什么 ③提醒 ④权限与保活 ⑤出网 ⑥怎么纠正。每行 ✅/⚠️/❌ 三档 + 一句人话 |
| 首启引导 | ✅ | `ZhuliSetupDialog` 两页：昵称人格（FlowRow 三档）→ 权限页 |

> 这里踩过的坑值得记：`pm grant` 对**未声明**的权限返回 exit 0（静默成功），所以"授权成功"必须再 `dumpsys package` 核 `granted`——否则界面全是假绿勾。

## 三、数据怎么流动（四条链路）

```
① 采集链
   通知/短信/分享/链接/图片
        │  NoiseGuard 四道护栏（静音/回声/低信号/去重）
        ▼
   inbox 表 ──pending_extract──→ 规则抽取（分类/时间/金额/取件码/周期）
        │                              │
        │                              ├─→ ledger（账本）
        │                              ├─→ reminders + AlarmManager（闹钟）
        │                              └─→ embeddings（256 维）
        ▼
② 提醒链
   reminders ──AlarmManager 三级降级──→ 到点通知（完成/稍后/撤销）──→ 写日历

③ 问答链（不联网优先）
   用户一句话 ──► 关键词意图路由 ──命中──► 查库 + 模板直答（毫秒级）
                        │
                        └─未命中──► 云端模型 + 6 工具 ──► 工具回库查 ──► 模型作答
                                        │
                                        └─ PrivacyRouter 三档闸门 ──► cloud_log 留档

④ 自检链
   14 行取真实状态（权限/库/闹钟/出网）──► 一屏回答"它现在到底行不行"
```

**设计上的取舍**：能规则算的绝不联网（分类、时间、金额、取件码、周期、常见问句）；模型只负责"听不懂的话"和"组织人话"。所以断网、没 Key、模型额度耗尽时，主干功能仍然可用。

## 七、下一刀该切哪

按现在的状态，卡点不在"功能不够"，在**三处没有数的东西**：

1. **漏收率**：通道齐了，但"系统通知弹出数 vs 入库数"从来没对过。没这个数，"采集完整性"就是没验收。
2. **集成测试为零**：149 个单测全是纯函数，UI 和系统交互靠手点。每次改装都要重跑 40+ 项手工验收，这是最大的时间黑洞。
3. **库是明文**：`P-2`。对一个主打"数据不出机"的产品，这一条是逻辑硬伤——本地明文库让"不出机"的承诺只对了一半。

对应建议顺序：先补漏收率（一次性、有结论）→ 再补关键路径的集成测试（把手工验收脚本化）→ 再定 SQLCipher 时机。
