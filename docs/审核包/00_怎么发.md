# 怎么发给网页版 AI（操作清单）

## 一、先明确：不要发整个项目

| 别发 | 原因 |
|---|---|
| `zhuli.7z`（107MB） | 网页版几乎不解析这种大包；就算能传，也是把 19 万行 fork 代码塞进去，AI 只会泛泛而谈 |
| `fixtures/realdev_20261121/*.db`、`fixtures/backup_drill/*.db` | **真实收件箱**：微信聊天、短信、快递取件码、账本全在里面。传上去等于把生活记录交给第三方 |
| `zhuli_secure_2026-11-20.xml` | API Key 密文 |
| keystore / `keystore.pass` / `cloud_api_key.txt` | 签名和密钥 |
| 原始验收截图（12 张） | 图里有微信联系人名、快递单号、取件码 → **要发先打码** |
| 整个 `fixtures/` 目录 | 混着真实数据与设备 dump |

一条判断标准：**凡是"真实发生在你手机上的内容"，都不发；凡是"描述这个项目的文字"，都可以发。**

## 二、推荐发法：分两轮，别一次问完

### 第一轮 · 审"情况"（现在就能发）

只发一个文件：

```
审核包/01_项目审核包_zhuli.md
```

这份已经把项目、进度、证据、缺陷、自评风险、10 个待答问题都写全了（去标识化过，可直接整篇粘）。
配一句开场白（可直接复制）：

> 这是一个我独立开发的安卓项目，非商业、单人维护。附件是我自己写的状态说明，我怀疑其中存在自我美化，请以"证据是否成立"为标准做独立评审，尤其针对第 8 节自评风险和第 9 节的 10 个问题逐条回答。不要给鼓励性评价。

### 第二轮 · 审"代码"（要看情况再发）

如果第一轮结论是"方向没问题、细节要看代码"，再追加：

1. 自研 `Zhuli*.kt` 40 个文件（4,224 行）——打包成一个 txt 或直接贴，这是唯一值得审的代码；
2. `CURRENT_STATE.md`（删掉 SHA-1 指纹和 keystore 路径两行）；
3. 数据库 schema + 迁移脚本。

**不要发上游代码**（`shared/`、`highlight/`、`document/` 等），那是 LastChat 的，审它没有意义，只会稀释注意力。

## 三、模型怎么挑

- 优先用**长上下文**的（能一次吃下几万字的那种），否则它只能读到片段就下结论。
- 别用"聊天型小模型"，这类评审需要它敢唱反调；找那种会指出"你这句话没有证据"的。
- 同一个包发给**两家不同的**，对比它们各自指出的问题——重合的部分大概率是真问题，只有一家说的多半是风格差异。

## 四、发出去之前，花 2 分钟自查这四件事

- [ ] 全文搜索 `sk-`、`key`、`pass`、`jks`，确认没有密钥；
- [ ] 全文搜索手机号、姓名、地址、快递单号；
- [ ] 确认没附 `.db` 文件、没附未打码截图；
- [ ] 网页版默认可能把对话用于训练 —— 这批内容可以接受再发（本包已去标识化）。

## 五、收回答案后

把它的结论**逐条对照** §6 的缺陷表和 §8 的自评风险：

- 它指出的问题你已经在 §6 写过 → 说明它读懂了，可信度加分；
- 它指出的问题你从没想到过 → 单独记下来，这是这次评审的净收益；
- 它只是在复述你写的话 → 换了家再问，或者把问题问得更具体（"第 5 条你凭什么说 CI 是最大崩盘点？"）。
